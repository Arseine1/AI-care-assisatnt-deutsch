# Décisions techniques – Jours 3 et 4

## Agent des cotisations piloté par un modèle local (outils, garde, comparatif) et mémoire

Détail, outils, tableau du comparatif : `docs/cotisations.md`. Résultats : `tests/resultats/sgb6-modeles.json`.

- **Le modèle choisit, le code contrôle et décide.** 10 outils au format « tools » de l'API de chat d'Ollama, schéma strict ; aucun outil valider ni refuser ; aucun paramètre de montant, de degré ni de résultat de règle. Le modèle ne voit jamais le questionnaire (résultats courts, sans nom ni numéro, alias « dossier-1 ») : une consigne cachée ne peut pas l'atteindre. Statut et montants viennent de `regles.js` ; les étapes omises par le modèle sont complétées par le code ; un compte rendu contradictoire est signalé.
- **Raison = paramètre `raison` de chaque outil** (et non le texte avant l'appel) : les petits modèles omettent le texte, le paramètre est validé par le schéma. Écart assumé avec la formulation « phrase de raison avant chaque appel ». Épurée (noms, adresse, numéros retirés) avant le journal.
- **Boucle déroulée en 12 tours dans n8n** (pas de cycle) : l'état circule d'un nœud à l'autre dans la session JSON, un nom unique par tour (pas d'ambiguïté d'indice d'exécution) ; la garde et les outils sont dans un sous-workflow (`97-sgb6-tour`) pour ne recopier le moteur qu'une fois. Journal (`choisi_par = 'modele'`, raison, accepté ou refusé), avancement et contrôle d'annulation après CHAQUE tour. Limites : 2 réponses invalides de suite, 12 tours, 15 minutes, 5 minutes par réponse ; abandon = mission guidée avec la mention.
- **Appels à une IA générative : 3 nœuds nommés, pas un de plus** (tests `chemins-ia` et `briques`) : rédiger (62), extraction SGB VI (93), pilote SGB VI par tour (93, 12 nœuds) et l'outil d'extraction par l'IA du sous-workflow 97. Température 0, num_ctx 8192 pour le pilote, keep_alive 30 min ; qwen3 : `think: false`.
- **Modèle réglable dans la page**, liste fermée côté n8n (`SGB6_MODELES`) : le nom envoyé par l'interface part dans une requête vers Ollama, il ne doit jamais être libre. La page affiche l'état « installé » de chaque modèle (lecture de `/api/tags`). Par défaut **qwen2.5:7b** (`SGB6_MODELE`) : seul modèle à mener les 3 cas du comparatif sans abandon, avec le moins de refus et le plus rapide. qwen3:8b (préféré de l'utilisateur) reste choisissable : exact mais 2 fois plus lent ici (mémoire), un abandon sur 3 ; llama3.1:8b abandonne 3 fois sur 3 (boucle de refus).
- **Mémoire** : poste de 15,9 Go, Ollama en natif Windows (un modèle de 5,5 à 6,7 Go chargé), conteneurs à 3,5-4,5 Go. `.wslconfig` passé de **11 Go à 8 Go** (sauvegarde : `%USERPROFILE%\.wslconfig.sauvegarde-11GB`) : avec 11 Go, Windows manquait de RAM quand un modèle était chargé (0,3 à 1 Go libres, swap, « segmentation fault » intermittents du CLI n8n pendant les imports). Prudence restante : décharger le modèle (`keep_alive: 0`) avant d'importer des workflows.
- **Veille du PC** : un saut d'horloge de 3 h pendant un essai long venait probablement d'une mise en veille ; la veille sur secteur est désactivée pendant les essais longs (`powercfg /change standby-timeout-ac 0`) puis remise à 15 minutes (valeur d'origine).
- **Limites** : comparatif sur 3 cas sur 9, un passage par cas ; le test de la page contre n8n n'a pas pu être fait dans le navigateur (session de test refusée par le contrôle d'actions), seulement en mode simulé.

## Cotisations retraite branchées à n8n (agent en tâche de fond, PostgreSQL, journal, dépôt, lecture facultative par l'IA)

Détail, webhooks, tables, tests : `docs/cotisations.md`. Résultats mesurés : `tests/resultats/sgb6-live.json`.

- **Le moteur de règles n'est pas réécrit pour n8n : il est recopié.** Un nœud Code de n8n ne peut importer aucun fichier ; `workflows/generer.mjs` colle `regles.js` tel quel dans chaque nœud qui s'en sert (la ligne `import` est remplacée par les valeurs légales, `export` est retiré) et embarque `caisse.json`. `tests/sgb6-n8n.test.mjs` vérifie que chaque copie contient exactement le fichier. Un seul code, trois usages : interface simulée, tests, n8n.
- **Tâche de fond sur le modèle du rapport d'étage** : ligne dans `soins.taches` (type `sgb6_agent`), battement de coeur à chaque étape, reprise au redémarrage de n8n et veilleur des workflows existants (rien à ajouter), résultat jamais réécrit si la tâche est annulée ou interrompue. **Journal et avancement écrits après chacune des 7 étapes**, avec contrôle d'annulation : le moteur est découpé en étapes (`demarrerTraitement`, `etapeControler`, `etapeCaisse`, `etapeRegles`, `etapeCalculer`, `etapeDeclaration`, `finaliserTraitement`), un nœud n8n par étape, l'état circulant en JSON ; `traiterQuestionnaire` les enchaîne et un test vérifie que les deux chemins donnent le même résultat. **Pause d'affichage de 1,1 s avant chaque étape** (le calcul prend quelques ms) pour que la page montre l'agent avancer, comme la petite pause du mode simulé : c'est un choix d'interface assumé (≈ 7 s par dossier), pas une lenteur réelle.
- **Aucun montant calculé sur une lecture par l'IA qui reste à vérifier** (cas b avec IA : 312,64 € affiché à tort, la moitié du bon montant, par parts égales appliquées à tort). Avec la lecture par l'IA, le montant n'est calculé que si tout est « ok » (champs valides, aucune règle ni écart incertain ou non, aucun document suspect) ; sinon « Montant non calculé : données à vérifier » dans la page, le brouillon (base de cotisation), les motifs et le journal. Règle plus stricte que « seulement si la valeur diffère de la caisse » : une lecture de modèle incertaine n'a pas à produire de chiffre. Sans IA, le comportement validé plus haut ne change pas (montant provisoire pour f, g, i).
- **L'IA ne recopie que des champs.** Consigne fixe, température 0, schéma JSON imposé par Ollama, questionnaire entouré de repères et présenté comme une donnée. Garde-fou ajouté : toute valeur lue par l'IA doit figurer dans le texte du questionnaire, sinon elle est écartée et comptée (« n'invente rien » vérifié par le code, pas seulement demandé). Échec, réponse illisible ou délai de 5 minutes dépassé : repli sur la lecture par les règles, signalé. Les consignes cachées sont repérées par le code sur le texte entier, pas par l'IA : même résultat avec ou sans lecture IA.
- **Deuxième appel à l'IA générative du dépôt, nommément** : `chemins-ia.test.mjs` et `briques.test.mjs` affirmaient « un seul nœud appelle `/api/generate` » ; ils listent maintenant exactement deux nœuds : `62-brique-rediger.json / Modèle de langue (Ollama)` et `93-sgb6-agent.json / Extraction SGB VI (Ollama)` (nœud renommé pour que le test le nomme). Tout autre appel, ou un renommage, fait échouer les deux tests. Un test vérifie que l'appel des cotisations a une consigne fixe, une température de 0 et un schéma imposé, et qu'aucun chemin ne va de l'IA au calcul sans passer par le contrôle de la réponse. `livrables.test.mjs` (température ≤ 0,2) passe tel quel.
- **Décisions jugées côté serveur sur le résultat enregistré**, jamais sur la requête : valider exige « prêt à valider » ET aucune règle ni aucun écart autre que « ok » (requête SQL sur le JSON enregistré) ; refuser exige un motif non vide et une exception ; une seule tâche de revue ; un dossier décidé ne peut ni être redécidé ni être retraité. La signature est celle de la session.
- **Journal sans donnée personnelle** : les lignes sont composées de comptes et de statuts (« 6 ok, 0 à vérifier, 0 non remplie(s) »), jamais de valeur extraite. Les noms et numéros ne vivent que dans `sgb6_dossiers` (nécessaire pour relire un dossier). Test réel : les noms, prénoms et numéros d'assurance des 9 questionnaires sont cherchés dans tout le journal.
- **Dépôt** : base64 dans le corps JSON (`.txt` ou `.pdf`, 1 Mo au plus, contrôlé deux fois : octets décodés, pas seulement la taille annoncée), PDF lu par le service OCR existant (`compose/ocr`) et **refusé s'il a fallu faire de l'OCR** (un scan n'est pas un « PDF contenant du texte »). Le document doit contenir au minimum la référence du dossier de la caisse et le nom de l'aidant. Un document suspect est accepté : l'agent le signale. Limite : le refus d'un scan arrive après la tentative d'OCR, donc pas instantanément.
- **Case « Lecture par l'IA »** : cochée par défaut en mode simulé (inchangé), **décochée en mode réel** (elle prend plusieurs minutes avec llama3.2).
- **Non fait** : lecture par l'IA des PDF scannés ; évolution du `valeurs-legales.json` pour 2027 (l'année absente est une exception explicite) ; test automatique de la page elle-même (vérifiée à la main dans le navigateur, mode réel).

## Page « Cotisations retraite » (branche cotisations-retraite) : moteur de règles, données fictives, mode simulé

- **Moteur en JavaScript pur** (`workflows/code/sgb6/regles.js`, module ES sans dépendance) : le même code sert l'interface (mode simulé), les tests et, plus tard, n8n. Il importe `data/sgb6/valeurs-legales.json` ; `definirValeurs()` permet à n8n de fournir ses propres valeurs. **Année absente = erreur explicite**, jamais de valeur par défaut (2030 testée).
- **Calcul en entiers (BigInt), arrondi au centime demi vers le haut à chaque étape** : base = Bezugsgröße × pourcentage × part, puis cotisation = base arrondie × 18,6 %. Raison : en virgule flottante, 625,2855 € (degré 5, prestation combinée) peut s'arrondir à 625,28 ; testé à 625,29. Valeurs exactes de la consigne toutes vérifiées (316,32 ; 735,63 ; 308,96 + 205,98 ; 198,62) et les 12 combinaisons recalculées indépendamment.
- **Pourcentages et paragraphes relus sur le texte de la loi** (gesetze-im-internet.de, 27.10.2026) : § 166 Abs. 2 Satz 1 SGB VI (tableau des pourcentages, identique à la consigne), Satz 2 (plusieurs aidants : répartition selon le Umfang de chacun), § 3 Satz 1 Nr. 1a (10 h par semaine sur au moins 2 jours, degré ≥ 2, à domicile, non professionnel) et Satz 3 (plus de 30 h de travail par semaine = pas d'affiliation). **Non relus** : § 5 Abs. 4 Nr. 1 SGB VI (R5, retraite à taux plein) et § 19 SGB XI (R2, définition de l'aidant) sont cités de mémoire ; à confirmer avant tout usage réel.
- **Numéro d'assurance retraite** : le chiffre de contrôle suit **§ 2 Abs. 6 VKVV** (https://www.gesetze-im-internet.de/vkvv/__2.html) : lettre remplacée par sa position dans l'alphabet sur 2 chiffres (A=01 … Z=26), nombre à 12 chiffres multiplié par 2 1 2 5 7 1 2 1 2 1 2 1, somme des Quersummen des produits, reste de la division par 10. Le texte de la loi ne donne pas d'exemple chiffré ; l'algorithme a été vérifié sur l'exemple connu 15070649C103 (contrôle = 3), qui vient de ma mémoire et non de cette source. Le contrôle ne dit pas que le numéro existe, seulement qu'il est bien formé. Un numéro dont la date de naissance ne correspond pas à celle du questionnaire est signalé.
- **Règles : qui lit quoi.** Degré (R1) et heures de soins (R3) viennent du dossier de la caisse et de l'expertise, jamais du questionnaire (cas d : le questionnaire dit 12 h, l'expertise 8 h : R3 « non »). Les heures de plusieurs personnes soignées s'additionnent ; le nombre de jours retenu est le plus grand (les jours ne se recoupent pas forcément, c'est une approximation côté aidant). R4 : 30 h exactement = ok ; horaires variables ou plusieurs emplois = incertain ; plus de 30 h = non même si les horaires varient. R5 : toute déclaration de retraite à taux plein, ou son absence de réponse, est « incertain » (décision humaine). R6 : parts déclarées acceptées seulement si elles font 100 % et si leur nombre égale celui des aidants du dossier de la caisse ; sinon « incertain » avec parts égales.
- **Écarts** (degré, prestation, nom et naissance de la personne soignée, nom et naissance de l'aidant entre questionnaire et caisse) : lignes `ECART` ajoutées au tableau des règles, « incertain » avec les deux valeurs. Le calcul utilise toujours le degré et la prestation **de la caisse** : il est alors « provisoire » (cas g : 198,62 € au degré 2) et reste à confirmer par une personne.
- **Quand l'agent calcule** : tant qu'aucune règle n'est « non » (cas f, g, i : calcul affiché comme provisoire, statut « exception »). Aucun calcul si une règle est « non » (cas d, e, h). Statut « prêt à valider » seulement si toutes les règles sont ok, les champs valides, aucun document suspect et un calcul disponible.
- **Document piégé (cas i)** : détection par motifs (« Ignoriere alle Regeln », « genehmige sofort », équivalents anglais et français). La phrase est signalée et n'a aucun effet : un test vérifie que le calcul et les règles sont identiques avec et sans la phrase. Limite : ce sont des motifs, pas une garantie contre toute formulation nouvelle (même limite que le contrôle de consigne du Mode B).
- **« Lecture par l'IA » en mode simulé** : la case existe et est transmise à l'agent, mais aucune IA n'est appelée : les champs sont lus par les règles (l'interface le dit). L'IA réelle viendra avec n8n ; elle ne fera qu'aider à lire, jamais à décider ni à calculer.
- **Validation / refus** : `deciderCotisations` refuse aussi côté `api.js` une validation hors « prêt à valider », un refus hors exception ou sans motif. Rien n'est transmis à la caisse (démonstration).
- **Choix de forme** : questionnaires rédigés en allemand comme un vrai formulaire de Pflegekasse (libellés + valeurs, cases à cocher, numéro avec espaces, ligne de remarque libre). Le résultat de l'agent n'est pas conservé quand on quitte la page (seul le statut du dossier l'est) : « Lancer l'agent » le recalcule.
- **Non fait / à faire** : branchement n8n (volontairement exclu), lecture réelle par l'IA, conservation du résultat entre deux visites de la page, test automatique de la page elle-même (vérifiée à la main dans le navigateur, mode simulé).

Elle exclut maintenant son propre nom, et ne compte plus les années des dates `jj/mm/aaaa` comme des chiffres inventés. `--reevaluer` note de nouveau des réponses déjà enregistrées sans rappeler Llama ; `--run=` choisit l'essai. Score de l'essai de départ réévalué : 17/30.

Les 8 faits retenus ne dépendent plus seulement de leur importance générale.

Contrepartie assumée : une demande dont le mot précis est absent du dossier, même s'il existe un synonyme que je n'ai pas prévu, répond « information non disponible » à tort. Les synonymes de `SYNONYMES` (brique-chercher-faits.js) sont à enrichir avec l'usage.

Les 10 variantes déguisées sont refusées ; 4 d'entre elles (D07–D10) ont été écrites avant la correction : 2 passaient, corrigées. Q16 : erreur 500 par perte de connexion de n8n à la base (0,7 Go de mémoire libre), puis 1 diagnostic sur 2 une fois rejouée. **Deux faux échecs de notation** corrigés après coup (H2 : « CIM-10 » ; Q07 : « 16 UI » d'un compte rendu scanné) : la liste de chiffres autorisés inclut maintenant la base de l'hôpital et les documents scannés. ## Jour 4 – Étape 7 : sécurité minimale (connexion du soignant, sessions, clé, origines) et broker fermé

Détail et limites : `docs/securite.md`. Tests : `node tests/securite.test.mjs` (hors n8n) et `node tests/securite-live.mjs` (contre n8n).

- **Connexion par identifiant + code PIN, PIN haché.** Le PIN est comparé à une empreinte `scrypt` (sel de 16 octets propre à chaque compte, comparaison à temps constant) ; il n'est conservé nulle part (ni base, ni journal, ni réponse). Raison : un PIN en clair en base serait lisible par quiconque accède à la base ; `scrypt` est fourni par Node (aucun module à ajouter dans n8n). Un identifiant inconnu fait le même calcul et reçoit le même refus qu'un mauvais PIN : rien ne révèle quels comptes existent.
- **Verrouillage : 5 échecs en 5 minutes** sur un compte existant → compte refusé même avec le bon PIN pendant le délai. Seuls les comptes existants sont comptés, pour que la table ne grossisse pas avec des identifiants inventés. Choix : fenêtre glissante calculée en SQL, sans tâche de nettoyage.
- **Session : jeton aléatoire de 32 octets, 12 heures, seule l'empreinte SHA-256 est en base.** Raison : une fuite de la base ne donne pas de session utilisable. Le jeton reste dans `sessionStorage` de l'onglet (effacé à la fermeture), jamais dans `localStorage`. La déconnexion supprime la ligne côté n8n.
- **Le contrôle de session est le PREMIER traitement de chaque point d'entrée**, ajouté par le générateur (`proteger` dans `workflows/generer.mjs`) à tous les webhooks sauf la connexion, le chemin interne et le courrier reçu : un test vérifie qu'aucun nœud n'est atteignable sans passer par « Session valide ? ». Sans session, la réponse est `{ "erreur": "session" }` et l'interface rouvre la connexion. Choix de la réponse HTTP 200 avec un motif plutôt qu'un 401 : n8n ne sait pas fixer le code d'état d'un webhook en mode « dernier nœud », et ce motif suffit à l'interface.
- **Le nom du soignant qui valide vient de la session, jamais du corps de la requête** (`valide_par` et `soignant_id`), écrit dans `soins.validations` (nouvelle colonne `soignant_id`) et dans le journal d'audit. Raison : sinon n'importe qui pourrait valider « au nom de » un autre soignant. Un test vérifie qu'un `valide_par` glissé dans la requête est ignoré.
- **CORS limité à l'adresse de l'interface** (`http://localhost` et `http://127.0.0.1`, ports 5173 à 5175 ; variable `AICARE_ORIGINES` pour en changer) au lieu de `*`.
- **Clé secrète `X-AICare-Cle` (credential n8n, valeur dans `.env`) : un filtre, pas un secret.** L'interface l'envoie, donc elle est lisible dans le code de l'interface. Gardée parce qu'elle écarte les appels qui ne viennent pas de l'interface ; la vraie protection est la session. Dit franchement dans `docs/securite.md`.
- **Chemin interne `aicare-verifier-interne` avec une clé distincte** (`AICARE_CLE_INTERNE`, jamais envoyée à l'interface, testée absente du code de l'interface). Raison : le workflow du courrier appelait « Vérifier le document » par HTTP sur le point d'entrée public ; ce point exige maintenant la session d'un soignant, qu'un courrier automatique n'a pas. Une exécution directe du workflow n'était pas possible : le point d'entrée répond tout de suite et continue l'analyse de l'IA en tâche de fond pendant plusieurs minutes, et un appel de sous-workflow aurait attendu la fin.
- **`courrier-recu` reste sans authentification** : Mailpit ne sait pas envoyer d'en-tête. Le webhook ne fait que déclencher la relecture de la boîte Mailpit par n8n (aucune donnée reçue, rien de lu ni de modifié par l'appelant). Limite documentée ; en production, n8n lirait la boîte en IMAP avec ses propres identifiants.
- **Comptes de démonstration fictifs** (`martin`, `keller`, `roth`), codes PIN de 6 chiffres tirés au hasard dans `.env` (`DEMO_PIN_*`), créés par `scripts/creer-soignants.mjs`. En mode simulé de l'interface : compte `demo` / `123456`, aucune vérification réelle.
- **Alarmes de capteurs affichées seulement dans leur page** (demande de l'utilisateur) : plus de bandeau sur les autres pages, seul le compteur rouge de l'onglet les signale. Risque noté : un soignant resté sur la page « Rapport de garde » voit le compteur et entend le bip, mais pas la carte.
- **Broker MQTT fermé** : `allow_anonymous false`, deux comptes aux droits séparés (`capteurs` publie, `n8n` lit), liste de droits `compose/mosquitto/acl`. Raison : un broker ouvert permettait à n'importe qui sur le réseau de déclencher de fausses alarmes. Mots de passe générés aléatoirement par `scripts/generer-secrets.mjs` dans `.env` ; le fichier haché est ignoré par Git et doit être lisible par l'utilisateur du broker (`chmod 644`), sinon le broker refuse de démarrer.
- **Pont TTN sans refonte** : un second déclencheur dans le workflow 81, qui traduit le message en sujet `capteurs/chambre{n}/{type}`. Le dépôt contient le nœud désactivé et sans compte ; l'importeur l'active avec les valeurs de `.env`. La clé TTN n'est jamais dans un workflow ni dans le dépôt (testé). Lecture seule du trafic, MQTT chiffré (8883), car le port 1883 du serveur TTN n'est pas chiffré. Seuls la chambre et le type d'alarme (liste fermée) sont repris d'un message TTN.
- **Les workflows sont écrits à la fin de la génération** (`generer.mjs`), parce que la protection des points d'entrée a besoin de tous les helpers ; les fins de ligne du code des nœuds sont normalisées.
- **Point ouvert** : pas de HTTPS, pas de rôles ni de gestion des comptes dans l'interface, jeton valable 12 heures même si l'onglet est fermé sans déconnexion (voir `docs/securite.md`).
## Jour 4 – Étape 6 : documents en automatique, et refonte de l'interface en trois pages

- **Trois processus métier, trois pages** (demande de l'utilisateur) : « Rapport de garde » (premier processus : un résident choisi une fois, deux modes au choix, Actions rapides et Consigne guidée, plus le rapport d'un étage entier), « Alarmes » (capteurs, avec bandeau d'urgence et signal sonore) et « Documents » (courriers et nouveautés de l'ePA, sans bruit). Une alerte de document n'apparaît jamais sur la page des alarmes de capteurs. Le bandeau d'urgence reste visible sur les autres pages, pour les seules alarmes de capteurs.
- **Courrier reçu** : Mailpit prévient n8n par webhook (**il n'a pas d'IMAP**, seulement SMTP et POP3 ; avec une vraie boîte KIM, le webhook se remplace par un « Email Trigger (IMAP) »). n8n ne lit que l'**identifiant** de la notification, relit le message par l'API de Mailpit, extrait le texte (OCR pour un scan), identifie le résident par le **code** (nom ET date de naissance, jamais deviné : cet identifiant ne dépend pas du modèle), indexe dans `a_verifier`, applique les règles de sécurité et crée une alerte (rouge, attention ou information) sur la page Documents.
- **Pièges mesurés** : (1) Mailpit n'envoie qu'**une notification par seconde** et abandonne les suivantes (5 lettres d'un coup : 1 seule notification) ; (2) régler `MP_WEBHOOK_LIMIT` à 50 aggrave le problème (même des messages espacés de 6 s sont perdus) : valeur par défaut gardée. **Rattrapage toutes les 2 minutes** (workflow 86) pour tout courrier non traité (rafale, notification perdue, n8n arrêté), avec un **verrou par courrier** (`soins.courriers_traites`, « en cours » pendant 15 minutes) : jamais de double traitement.
- **Validation → RAG** : seule la validation d'un rapport « Vérifier le document » peut faire entrer la lettre dans les sources d'intelligence (collection `patients`, type `lettre_validee`), et **seulement si les règles n'y ont trouvé aucune contradiction** ; avec contradiction, la validation est enregistrée mais la lettre reste « à vérifier » jusqu'à clarification par le médecin (décision à discuter : on ne fait pas entrer dans les faits fiables une lettre contradictoire).
- **Nouveautés de l'ePA** : une alerte d'information quand l'ePA d'un résident déjà importée reçoit du contenu nouveau ou modifié (la première importation ne notifie rien). Vérifié sur la requête réelle dans une transaction annulée ; les mocks ePA, arrêtés pour la mémoire, n'ont pas été relancés.
- **« Extraire_faits » n'identifie pas le résident** (contrairement à la formulation du brief) : l'identification par le nom et la date de naissance est faite par le code, car une erreur d'identité est plus grave qu'une lettre non rattachée.
- **Interface** : nouveau logo (icône du logo de l'utilisateur dans l'en-tête, favicon), connexion perdue signalée, tests de textes (`tests/i18n.test.mjs`).
- **Erreurs d'interface corrigées en cours d'étape** : une erreur de compilation (chaîne de caractères mal écrite dans la page d'historique) et des textes affichés en clés brutes (clé `alertes` en double dans `fr.json`) m'ont été signalés par l'utilisateur ; l'interface est désormais **vérifiée dans le navigateur avant d'être livrée**, en mode simulé et en mode réel.
- **Essai réel** (`node tests/courrier-live.mjs`, 16 vérifications) : courriers Weber (31 s), Fischer, inconnu, scan Wagner (110 s, OCR), renvoi sans doublon, message sans pièce jointe sans effet, validations (Fischer ajoutée, Weber refusée), ePA.

## Jour 4 – Étape 4 : tâches de fond fiables (battement de coeur, annulation, reprise)

- **Statuts** de `soins.taches` : `en_cours`, `termine`, `termine_avec_erreurs`, **`interrompue`** (n8n arrêté, ou sans signe de vie), **`annulee`** (demande du soignant). Colonne **`heartbeat`** écrite à la création et à chaque étape (avant chaque résident, avant l'extraction et avant la comparaison de l'analyse complémentaire, à chaque résultat).
- **Au démarrage de n8n**, toute tâche « en cours » passe à « interrompue » : `80-reprise-taches` démarre sur l'événement « Instance started » du nœud n8n Trigger (`init`). Aucune condition de délai : après un redémarrage, plus aucun travail ne peut tourner. Vérifié en réel (n8n redémarré avec une tâche « en cours » : interrompue en quelques secondes, événement `tache_interrompue` cause `redemarrage` au journal d'audit).
- **Veilleur** : toutes les 5 minutes, une tâche « en cours » dont le battement date de plus de **30 minutes** (le délai maximal d'une génération, fixé par le délai de l'appel à Ollama) passe à « interrompue » (cause `sans_signe_de_vie`). Vérifié sur la vraie requête : une tâche sans battement depuis 40 minutes est interrompue, une tâche vivante n'est pas touchée.
- **Annuler** : `POST /webhook/aicare-annuler {tache_id}` (UUID seulement). Seule une tâche « en cours » est annulée, une seule fois ; événement `tache_annulee` au journal. Le bouton « Annuler la préparation » (rapport d'étage) et « Annuler l'analyse complémentaire » (Vérifier le document) l'appellent.
- **Comment l'annulation est prise en compte** : avant chaque résident (et avant chaque étape lourde de l'analyse), une requête écrit le battement **et** vérifie que la tâche est encore « en cours » ; sinon, le résident est ignoré (aucune recherche, aucune génération). Les écritures de résultat (`Avancer la tâche`, `Terminer la tâche`, `Enregistrer l'analyse`) ne s'appliquent que si la tâche est encore « en cours » : **une annulation ou une interruption n'est jamais écrasée** par un résultat arrivé en retard.
- **Limite honnête** : on ne peut pas interrompre un appel déjà parti chez Ollama ; la génération en cours se termine (jusqu'à environ 3 minutes sur ce poste), son résultat est abandonné. Essai réel : étage 2 annulé après le premier résident ; 1 résident sur 4 traité, aucune génération lancée ensuite (observée pendant 6 minutes).
- **Les rapports déjà prêts restent utilisables** : après une annulation ou une interruption, l'interface les affiche, le soignant peut les relire et les valider ; il est invité à relancer l'étage pour les autres.
- **Fragilité observée** : pendant l'essai, n8n a perdu quelques dizaines de secondes sa propre connexion à PostgreSQL (« timeout exceeded when trying to connect », 0,6 Go de mémoire libre sur 8 Go) puis l'a retrouvée ; une tâche en route s'est terminée en `termine_avec_erreurs`. L'essai réel réessaie donc ses appels. Sur le poste de déploiement (16 Go) le risque est moindre ; à surveiller.
- **Tests** : `node tests/taches.test.mjs` (12 tests, graphes et requêtes) et `node tests/taches-live.mjs` (essai réel : veilleur, annulation, redémarrage de n8n, annulation d'un vrai rapport d'étage ; `--etage` pour rejouer seulement la dernière partie).

## Jour 4 – Étape 1 : filtre anti-invention (« 0 phrase non sourcée »)

- **Constat** (essai de l'étage 2, Llama 3.2) : un petit modèle écrit des phrases que les sources ne contiennent pas (« diurèse importante », « ajuster la dose d'anti-histaminiques »). Les avertissements les signalaient sans les empêcher. Un prompt ne peut pas le garantir : c'est le code qui doit l'imposer.
- **Le modèle ne rédige plus un texte libre.** Pour les cinq prompts de texte (`generer_sbar`, `resume_epa`, `points_vigilance`, `contexte_alarme`, `consigne_guidee`, `sortie: phrases`), il renvoie un JSON `{"phrases": [{"section", "phrase", "source_id"}]}`. Ce format est **imposé par Ollama à la génération** (sortie structurée avec un schéma JSON, y compris l'énumération des rubriques) et pas seulement demandé dans le prompt ; vérifié sur Ollama 0.40.9 avec Llama 3.2.
- **Chaque fait porte un identifiant** (F1, F2…) dans le bloc FAITS DES SOURCES ; la phrase désigne le fait dont elle vient. Une phrase = un seul fait (plus de fusion de faits de sources différentes).
- **Un contrôle codé, sans IA**, dans le nœud « Contrôler la réponse », retire toute phrase dont : l'identifiant n'est pas un fait fourni ; un chiffre, une dose, une heure ou une date n'est pas dans CE fait ; un médicament (liste de terminaisons + noms suivis d'une dose dans les faits) n'est pas dans CE fait ; un jugement (« élevé », « important », « stable »…) n'est pas formulé par CE fait ; au moins 40 % des mots de contenu (au moins 2) n'y sont pas ; un autre résident est mentionné ; ou la phrase est en double ou hors rubrique.
- **Le texte est assemblé par le code** : titres des rubriques, phrases gardées, et la source ajoutée entre crochets **d'après le fait cité** (le modèle ne peut plus citer une source de travers). Une rubrique sans phrase affiche « information non disponible. », écrit par le code.
- **Les phrases retirées sont conservées à part** (`retirees`, colonne `soins.brouillons.retirees`, nombre au journal d'audit) et affichées dans une section repliable « Retiré car non sourcé » : le soignant voit tout ce qui a été écarté, rien de cela n'entre dans le texte, ni dans la validation, ni dans le RAG, ni dans la transmission.
- **Un JSON invalide ne donne aucun texte** ; un JSON coupé par la limite de longueur est récupéré phrase par phrase (la dernière, incomplète, est ignorée).
- **Compromis assumé** : le contrôle est strict, il peut retirer une phrase correcte mal formulée. Mieux vaut un rapport plus court qu'une phrase inventée en garde de nuit. Les anciens contrôles (attribution, termes, répétitions…) tournent ensuite sur le texte assemblé et restent des avertissements.
- **Négations** : une négation du fait ne peut pas être perdue ni ajoutée (« pas de perte de connaissance » ne devient jamais « perte de connaissance » : les deux phrases partagent tous leurs mots, seul ce contrôle les distingue). « Pas de » et « sans » sont équivalents.
- **Limite** : le filtre vérifie que la phrase est appuyée par son fait, pas que la formulation en conserve tout le sens (inversions plus subtiles, ordre des événements, causalité). La relecture du soignant reste obligatoire.
- **Prompts passés en 1.1.0** (`consigne_guidee` 1.2.0) et règles en 1.3.0 ; le fichier `prompts/tests/points_vigilance.json` a été corrigé (la réponse de référence fusionnait deux faits).
- **Tests** : `node tests/anti-invention.test.mjs` (19 tests : heures, valeurs, doses, jugements, médicaments, mauvais fait, injection, doublon, JSON invalide ou coupé, mutation de chaque nombre de chaque fait) et `tests/prompts.test.mjs` (réponses de référence converties en JSON).

## Jour 3 – Étape 4 : rapport de garde (par résident et par étage), ajout au RAG et transmission

- **Le rapport de garde SBAR (12 dernières heures) existe à deux échelles** : un résident (bouton existant, `aicare-action`) et un étage entier (`aicare-etage`). Pour un étage, le prompt est **fixé à `generer_sbar`** dans n8n et l'interface n'envoie qu'un numéro d'étage (un nombre entier, contrôlé) : aucun texte libre.
- **Étage = tâche asynchrone.** Un rapport prend 2 à 6 minutes ; un étage de 4 résidents en demande 10 à 25, bien au-delà d'une requête HTTP raisonnable. `aicare-etage` crée une ligne dans `soins.taches`, **répond tout de suite** (nœud « Répondre » en cours de workflow) et continue ; l'interface consulte `aicare-tache` toutes les 4 secondes et affiche chaque rapport dès qu'il est prêt. Les résidents sont traités **l'un après l'autre** (`Execute Workflow` en mode « chaque élément ») : l'ordinateur de 8 Go ne fait pas tourner deux générations à la fois. Une erreur sur un résident est notée dans la tâche (`termine_avec_erreurs`) et n'arrête pas les autres.
- **Une seule brique de rédaction pour tous les chemins** : le sous-workflow `67-brique-rapport-garde` enchaîne les mêmes briques que le Mode A (chercher, template verrouillé, rédiger). Aucun nouvel appel à l'IA ; un test vérifie qu'aucun des nouveaux workflows ne contient `/api/generate`.
- **La tâche ne garde que des brouillons.** Rien n'est enregistré comme validé tant que le soignant n'a pas cliqué sur « Valider l'étage ». Chaque rapport reste modifiable avant la validation.
- **Après validation, deux effets, dans une brique commune (`66-brique-apres-validation`)** : (1) le texte validé est **ajouté au RAG** (collection `patients`, source « Rapport validé », type `rapport_valide`, rattaché au résident) par l'Indexeur existant (anti-doublon par empreinte SHA-256) ; (2) il est **transmis à l'équipe suivante** par un message envoyé dans Mailpit (la boîte simulée, comme KIM) et noté dans `soins.transmissions`. Le journal d'audit reçoit les événements `ajout_rag` et `transmission`.
- **Le texte ajouté au RAG et transmis est relu dans la table des validations**, par identifiant numérique de validation, jamais pris dans la requête reçue : on ne transmet que ce qui a été enregistré après contrôle du brouillon. Seule une validation dont l'action est `generer_sbar` déclenche ces deux effets ; un résumé ePA, des points de vigilance ou une réponse de consigne validés sont enregistrés mais ni transmis ni ajoutés au RAG.
- **Validation d'un lot** (`aicare-valider-lot`) : chaque rapport passe individuellement par la brique « enregistrer » (brouillon exigé, une seule validation par brouillon), puis **un seul message** regroupe l'étage. Un rapport refusé (déjà validé, introuvable) n'empêche pas les autres ; il est listé dans la réponse.
- **Un échec de transmission ne défait pas la validation.** Le statut `echec` est noté, l'interface le dit clairement (« l'équipe suivante n'a pas été prévenue ») au lieu de l'afficher comme un succès.
- **Un rapport validé n'est jamais relu comme un fait par un nouveau rapport.** Sinon les erreurs éventuelles d'un SBAR passé (ou ses oublis) seraient recopiées dans le suivant. « Chercher » ignore le type `rapport_valide` sauf si le prompt le demande (`rapports_valides: true` en tête du fichier ; seul `consigne_guidee`, passé en 1.1.0, le fait). Un soignant peut donc interroger l'historique en Mode B, avec la source « Rapport validé » bien visible.

- **Limites** : pas d'identité du soignant (`valide_par` reste « soignant (non identifié) » tant qu'il n'y a pas d'authentification) ; une seule équipe suivante ; la tâche en cours ne peut pas être annulée depuis l'interface ; si n8n redémarre pendant un étage, la tâche reste « en cours » (à relancer).

## Jour 3 – Étape 1 : briques réutilisables (chercher, template, rédiger, enregistrer, journal)

- **Cinq sous-workflows n8n** (`workflows/60`–`64`) assemblés plus tard par les workflows d'entrée de l'interface ; description complète dans `docs/briques-ia.md`. Un banc d'essai (`65`, `test-briques` et `test-enregistrer`) permet de les tester de bout en bout, sans aucun texte libre.
- **Un seul endroit envoie du texte à l'IA : « rédiger », et seulement le prompt produit par « template ».** « rédiger » refuse tout texte qui n'a pas les blocs du template ; « template » n'accepte que la sortie de « chercher ». Vérifié par `tests/briques.test.mjs` (un seul nœud `/api/generate` dans tous les workflows).
- **Template en 4 blocs verrouillés** (RÔLE ET RÈGLES, FAITS DES SOURCES, INSTRUCTION SOIGNANT, FORMAT DE SORTIE) : un faux bloc glissé dans un fait ou une consigne devient `(bloc)` ; les crochets d'un fait deviennent des parenthèses, donc seule une vraie source peut apparaître entre crochets. Les règles désignent les blocs sans crochets (« le bloc FAITS DES SOURCES ») pour qu'un marqueur n'apparaisse qu'une fois dans le prompt : un test l'a révélé (3 occurrences au départ).
- **Les faits sont des données, pas des ordres** (règle 5) : une note ou une lettre contenant « ignore les règles » ne doit pas être exécutée.
- **« chercher » lit le logiciel de soins en DIRECT et le RAG pour le reste.** Le RAG n'étant actualisé que 4 fois par jour, un rapport des 12 dernières heures qui s'appuierait seulement dessus manquerait la chute de ce matin. Le RAG est toujours filtré par `patient_id` (et par période pour les événements) ; les contenus du logiciel de soins ne sont pas relus dans le RAG (pas de doublon).
- **Les lettres non contrôlées (`a_verifier`) ne sont jamais des faits** : elles sortent à part (`lettres`).
- **Prompts : fichiers Markdown versionnés dans `prompts/`**, intégrés aux workflows à la génération (pas de lecture de fichier à l'exécution) ; la version utilisée est écrite dans chaque brouillon et dans le journal. Le générateur refuse un prompt incomplet.
- **Brouillons (`soins.brouillons`) : l'enregistrement n'est possible que pour un brouillon existant.** « enregistrer » ne peut donc pas être appelé avec un texte qui ne vient pas d'une génération ; il marque le brouillon `valide` et écrit la validation dans une seule requête, ce qui interdit la double validation (testé : 2e validation refusée, brouillon inconnu refusé). `modifiee` est calculé en comparant le texte validé au texte de l'IA. Le brouillon est un texte de l'IA non validé, jamais présenté comme un résultat.
- **Journal d'audit `soins.journal_ia`** : génération, validation, validation refusée, avec prompt, version, modèle, durée et types d'avertissements ; le texte généré n'y est pas copié.
- **Contrôle automatique de la réponse** (source inconnue, ligne sans source, nombre ou heure absent des faits, chiffre absent de la source citée, autre résident, JSON invalide) : il **signale** sans corriger, et ne remplace pas la relecture. Premier essai réel (M. Weber) : aucun fait inventé, mais l'IA citait une source par paragraphe au lieu d'une par phrase ; le prompt SBAR passe en v1.0.1 (une phrase par ligne, une source par ligne) et le contrôle en v. « par ligne ».
- **Requêtes SQL paramétrées** (`$1`, `$2` via `queryReplacement`) : aucune valeur n'est concaténée dans le SQL.
- **Modèle : réglage unique `AICARE_MODELE` (défaut `llama3.2`), température 0,1, graine fixe, contexte 4 096, 500 tokens, pénalité de répétition 1,2.** Mesures sur ce poste (8 Go de RAM, processeur seul) : 1,8 token/s pour Llama 3, 4,4 token/s pour Llama 3.2 (3 milliards). Un rapport SBAR complet a pris **environ 16 minutes** pour M. Weber ; celui de M. Becker a **dépassé la limite de 15 minutes** de l'appel à Ollama et a échoué. La limite est portée à 30 minutes ; **par accord avec vous, les essais se font avec Llama 3.2** (3 à 6 minutes par rapport). Le modèle se change avec `AICARE_MODELE` (`node workflows/generer.mjs`).
- **Qualité mesurée avec Llama 3.2 sur 6 vrais essais** : le modèle a recopié les faits au lieu de rédiger (v1.0.2), inventé une action (« contrôle prévu à 14h13 »), qualifié des valeurs (« pouls anormal », « situation préoccupante »), attribué un fait à la mauvaise source, présenté des glycémies de contrôle comme des hypoglycémies, et **bouclé en répétant les mêmes lignes** jusqu'à la limite. Un exemple écrit dans le prompt (« Chute constatée à 04h41 ») a même été recopié comme un fait de M. Becker : **aucun exemple concret n'est plus donné dans les prompts**. Réponses : règle « ne pas qualifier une valeur » (règles v1.1.0), pénalité de répétition, longueur limitée, et 8 contrôles automatiques (voir docs/briques-ia.md), tous déclenchés sur de vrais textes. **Conclusion honnête : le dispositif signale les écarts mais ne les supprime pas ; un modèle plus grand (Llama 3 8B sur un poste plus puissant) et la relecture du soignant restent indispensables.**

Elles ne polluent donc pas `patients`.

## Jour 2 – Étape 6 : documentation des schémas

- **`docs/schema-rag.md`** : collections, index, dictionnaire du payload, règles d'identifiant et d'empreinte, ce que produit chaque connecteur, règle d'identification, exemples, recette d'interrogation (avec le filtre « 12 dernières heures », vérifié), correspondance des identifiants et journal. Un schéma Mermaid résume le flux.

## Jour 2 – Étape 5 : planification, anti-doublon et journal

- **Planification : 4 fois par jour, et non toutes les 5 minutes** (consigne mise à jour : « toutes les 5 min » remplacé par « 4 fois par jour »). Toutes les 6 heures : 00:00, 06:00, 12:00 et 18:00 (heure de Berlin, `timezone` fixé dans chaque workflow). Les 4 connecteurs sont **décalés de 10 minutes** (soins :00, FHIR :10, fichiers :20, ePA :30) pour ne pas solliciter Ollama et la mémoire du poste en même temps. Conséquence à connaître : une information du logiciel de soins peut attendre jusqu'à 6 heures avant d'être dans le RAG ; les webhooks `import-*` permettent un import immédiat, et la fréquence se change en modifiant `HEURES` dans `workflows/generer.mjs`.
- **Anti-doublon par empreinte SHA-256, vérifié AVANT l'embedding** : l'Indexeur lit le journal (une seule requête pour tous les morceaux), ne garde que les empreintes inconnues, et ne vectorise ni n'envoie à Qdrant ce qui n'a pas changé. Mesuré : passage 1 = 93 morceaux importés ; passages 2 et 3 = 0 importé, 93 ignorés. Cela économise surtout le temps d'embedding, très lent sur ce poste.
- **Double protection** : l'identifiant de point Qdrant est stable (source, référence, numéro de morceau). Même si le journal était vidé, ré-importer écraserait les mêmes points au lieu de les dupliquer.
- **Un morceau modifié est ré-importé** : son empreinte change, il passe l'anti-doublon et remplace le point existant. Le journal garde les anciennes versions (historique d'audit), avec contrainte `UNIQUE(source, empreinte)`.
- **Journal des imports (`soins.journal_imports`)** : une ligne par morceau (source, référence#morceau, patient_id, empreinte, collection/type, date), écrite **seulement après** le succès de l'écriture dans Qdrant : un échec en cours de route n'est jamais marqué comme importé et sera retenté au passage suivant.
- **Branche « rien de nouveau »** : si tous les morceaux sont connus, le workflow renvoie `{morceaux_indexes: 0, ignores_deja_importes: n}` sans appeler Ollama ni Qdrant.
- **Test automatisé `tests/test-du-soir.mjs`** : 3 passages des 4 connecteurs ; vérifie le nombre de points stable, aucun couple source/référence/morceau en double dans les 3 collections, journal stable sans empreinte en double, et que « M. Weber chute » renvoie au moins 3 sources.
## Jour 2 – Étape 4 : workflows n8n connecteurs

- **Architecture : 4 connecteurs + 1 sous-workflow « Indexeur » commun** (`workflows/00-indexeur.json`). Chaque connecteur ne fait que « lire sa source et produire des documents » ; le découpage, l'embedding et l'écriture dans Qdrant sont écrits une seule fois. Ajouter une source (ex. KIM) = un connecteur de plus, sans toucher à l'Indexeur.
- **Les workflows sont générés** (`node workflows/generer.mjs`) à partir de fichiers `workflows/code/*.js` : le code de chaque nœud est un vrai fichier lisible, relisible et testable hors n8n (`tests/indexeur-decoupage.test.mjs`), au lieu d'être noyé dans du JSON. Les JSON générés sont versionnés (c'est ce qu'on importe) ; `node workflows/importer.mjs` les importe, publie les déclencheurs et redémarre n8n.
- **Aucun secret dans les workflows** : le mot de passe PostgreSQL est un credential n8n créé par `importer.mjs` à partir du `.env` ; les JSON ne contiennent que son identifiant. Les adresses (Qdrant, Ollama…) sont écrites en dur dans les nœuds, car n8n 2 bloque l'accès aux variables d'environnement dans les nœuds.
- **n8n 2 : un sous-workflow doit être publié**, sinon l'appel échoue (« Workflow is not active »). `importer.mjs` publie donc aussi l'Indexeur.
- **Découpage 300–500 mots** (cible 400, jamais plus de 500, un dernier morceau court est rattaché au précédent) : un document de moins de 500 mots reste entier. Une note de soins (30 à 60 mots) reste donc **un seul morceau avec sa date exacte** : fusionner les notes d'une journée en blocs de 300 mots détruirait le filtre « 12 dernières heures ». Le découpage joue pour les documents longs (protocoles, lettres, textes OCR).
- **Identifiant de point Qdrant stable** = hash de (source, référence, numéro de morceau) : ré-importer le même document écrase le même point, jamais de doublon, même sans journal. **Empreinte SHA-256 du contenu** (texte + date + patient + type) dans le payload : elle sert à l'anti-doublon et au journal de l'étape 5 (ne pas ré-embedder ce qui n'a pas changé).
- **Le nom du résident est ajouté au texte vectorisé** (« M. Hans Weber (chambre 12) – … ») et le préfixe `search_document:` de nomic-embed-text est utilisé : sans cela, la recherche « M. Weber chute » ne retrouve pas les morceaux d'un résident précis.
- **Un seul `patient_id`** : les connecteurs FHIR et ePA retrouvent le résident par la table de correspondance (identifiant FHIR, KVNR), jamais par le nom.
- **Fichiers : OCR par un petit service** (`compose/ocr`, OCRmyPDF + Tesseract deu/fra/eng, appelé en HTTP). Un PDF avec texte est lu avec pdftotext (rapide, fidèle) ; seuls les scans passent par l'OCR. Choisi parce que le nœud « Exécuter une commande » de n8n 2 est désactivé et que n8n n'a pas accès à Docker. Le dossier `data/fichiers/` est monté en lecture seule dans `~/.n8n-files` (seul dossier lisible par n8n 2).
- **Rattachement des documents scannés** : un document est rattaché à un résident seulement si **le nom ET la date de naissance** du texte correspondent à un seul résident (les homonymes ne se distinguent que par la date). Sinon il va dans `a_verifier` (`identite_inconnue` ou `identite_ambigue`) : on ne devine jamais une identité.
- **FHIR : réponse forcée en JSON** (`Accept: application/fhir+json` + format de réponse JSON) : HAPI renvoie du HTML sinon, et le type `application/fhir+json` n'est pas reconnu comme JSON par n8n. `_lastUpdated` sert de date aux documents : elle ne change que si la ressource change. On relit toujours la liste complète d'un type pour reconstruire le document entier d'un résident (jamais un morceau partiel qui écraserait le reste).
- **ePA lue en FHIR JSON** (accès direct, sans VAU) et filtrée sur le KVNR ; les patients des exemples de gematik, inconnus de la maison, sont ignorés.
- **Postgres : `executeOnce`** sur les nœuds qui suivent un nœud à plusieurs lignes : n8n exécute un nœud une fois par élément reçu, ce qui avait produit 351 morceaux au lieu de 47 (bug trouvé et corrigé).
- **Hors périmètre de cette étape** : planification toutes les 5 minutes, anti-doublon par empreinte avant embedding et journal des imports (étape 5). La **boîte KIM (lettres de médecin dans Mailpit) n'a pas encore de connecteur** : elle n'était pas dans la liste des 4 workflows demandés ; c'est elle qui alimentera `a_verifier`.
- **Résultat mesuré** (une exécution de chaque connecteur) : 47 morceaux (logiciel de soins) + 24 (FHIR) + 16 (ePA) + 1 scan (fichiers) = 88 dans `patients` ; 5 protocoles dans `connaissances`. La recherche « M. Weber chute » renvoie des morceaux du logiciel de soins, de l'ePA et de la base de l'hôpital.
## Jour 2 – Étape 3 : collections Qdrant et correspondance des identifiants

- **3 collections, 768 dimensions, distance Cosine** (`patients`, `connaissances`, `a_verifier`) : 768 = dimension de `nomic-embed-text`, vérifiée sur un vrai embedding (point de test inséré, retrouvé avec un score de 1,0, puis supprimé). Cosine convient aux embeddings de texte (seul l'angle compte, pas la longueur).
- **Rôle de chaque collection** : `patients` = morceaux rattachés à un résident (une seule collection filtrée par `patient_id`, plutôt qu'une par résident : plus simple à interroger et à planifier) ; `connaissances` = protocoles, sans patient ; `a_verifier` = documents entrants à contrôler (lettres, identité ambiguë, contradiction), séparés pour qu'une information non vérifiée ne soit jamais présentée comme fiable.
- **Index de payload** sur les champs filtrés : `patient_id`, `chambre`, `source`, `type`, `empreinte` (keyword), `date` (datetime, pour « les 12 dernières heures »), plus `theme` (connaissances) et `statut`/`motif` (a_verifier). Sans index, les filtres Qdrant sont lents dès que la collection grossit.
- **Création sans suppression** : le script ne recrée jamais une collection ; s'il en trouve une avec une autre dimension ou distance, il s'arrête au lieu d'effacer des données.
- **Un seul `patient_id` (`PAT-00x`) pour tous les systèmes** via `soins.correspondance` (logiciel de soins, FHIR, KVNR de l'ePA, capteur, chambre) et la vue à plat `soins.v_correspondance`.
- **Fonctions SQL de résolution** : `soins.resoudre_patient(système, identifiant)` et `soins.trouver_par_identite(nom, date de naissance)`. Pour les homonymes, elle renvoie 0 ligne si inconnu et ne devine jamais : l'appelant range alors le document dans `a_verifier`. Index unique `(nom, prénom, date de naissance)`.

## Jour 2 – Étape 1 : données de test

- **Source unique `data/source/residents.mjs`** : SQL, bundle FHIR et liste du front sont générés depuis ce fichier, pour que les 8 résidents soient identiques dans toutes les sources d'intelligence (pas de dérive entre systèmes).
- **Schéma PostgreSQL `soins`** (et non `public`) : le logiciel de soins fictif ne se mélange pas avec les tables internes de n8n qui vivent dans la même base. `journal_imports` et `validations` n'ont volontairement pas de clé étrangère : recharger les données de test ne doit pas effacer l'historique des imports ni des validations.
- **Horodatages en SQL relatif (`now() - interval`)** et heures écrites dans le texte calculées par SQL : les « 12 dernières heures » sont toujours fraîches et le texte (« chute à 04h41 ») est toujours cohérent avec l'horodatage. Conséquence : l'heure littérale « 2h40 » demandée n'apparaît que si le chargement est fait vers 7h40 ; la chute est toujours placée 5 heures avant le chargement.

La lettre « Herr Müller » comporte volontairement une contradiction (cotrimoxazole) qui n'existe que pour le résident né le 01.12.1947 (allergie aux sulfamides) : rattachée au mauvais Müller, l'alerte disparaîtrait. Le sélecteur du front affiche prénom et date de naissance pour lever le doute.

Le « scan » est une image (bruit, léger décalage de lignes) sans texte sélectionnable, pour exiger l'OCR. Police système utilisée pour dessiner le scan (Arial/DejaVu).

- **Mailpit sans doublon** : avant chaque envoi, suppression des messages portant le même objet.
- **Correctif compose : HAPI en root** (`user: "0:0"`) : l'image tourne par défaut en utilisateur non privilégié et ne pouvait pas écrire dans le volume H2 (le conteneur redémarrait en boucle, 61 fois). À durcir avant tout déploiement.

# Décisions techniques – Jour 1

## Étape 7 — Alertes, réponses fictives et couche api.js

- **`api.js` est le seul point d'accès aux données** : l'interface n'appelle que `demander()` et `enregistrer()`. Passer à n8n au jour 3 = mettre `VITE_MOCK=false`, sans réécrire l'interface.
- **Interrupteur `VITE_MOCK` (défaut `true`)** lu dans le `.env` de la racine (`envDir: '..'` dans `vite.config.js`). Seules les variables préfixées `VITE_` sont visibles du navigateur : les mots de passe du `.env` ne sont jamais exposés au front.
- **Contrat avec n8n** : Mode A `POST /aicare-action {action, chambre}` ; Mode B `POST /aicare-consigne {chambre, consigne}` ; validation `POST /aicare-valider {…, texte, sources, modifiee}`. Réponse : `{texte, sources[], alertes[{type, message}]}`. Les noms de webhooks pourront changer au jour 3.
- **`mock.json`** : une réponse simulée par action + une pour le Mode B, avec variables `{resident}`, `{chambre}`, `{consigne}` ; données fictives (ex. M. Weber, chambre 12). Les sources citées reprennent les sources d'intelligence : logiciel de soins, ePA, lettre de médecin, base hôpital (FHIR), capteurs, Télématique Infrastructure (système de santé allemand).
- **Bandeau rouge sous l'en-tête, pleine largeur** (et non dans la colonne de réponse) : sur tablette en portrait la réponse est plus bas, l'alerte doit rester visible sans défiler. `role="alert"` pour les lecteurs d'écran. Deux types : alarme capteur et contradiction entre documents.
- **Scénarios d'alerte du mock** : rapport de garde et points de vigilance → alarme capteur de lit (LoRaWAN) ; vérifier le document → contradiction (amoxicilline prescrite / allergie à la pénicilline). Résumé ePA et Mode B → aucune alerte.
- **États de chargement et d'erreur** : message pendant la génération (boutons désactivés pour éviter les doubles demandes) ; en cas d'échec d'enregistrement, le texte du soignant est conservé.
## Étape 6 — Réponse et validation

- **Forme d'une réponse : `{ texte, sources[] }`** : le texte contient déjà les citations entre crochets ; la liste des sources est répétée sous forme d'étiquettes `[Logiciel de soins]`, `[ePA]`… pour les voir d'un coup d'œil. Cette forme sera celle du webhook n8n.
- **Zone de texte modifiable avec indicateur « modifiée »** : le soignant garde la main ; on sait si le texte validé diffère de celui de l'IA (`modifiee` est transmis à `onValider`, utile pour la traçabilité).
- **Toute modification annule la validation précédente** : on ne peut pas croire qu'une version éditée après coup est enregistrée.
- **Validation = confirmation affichée avec l'heure** ; l'enregistrement réel (n8n / base) sera branché via `api.js` à l'étape 7 et au jour 3. Bouton vert (couleur de validation), désactivé si le texte est vide.
- **Rappel « relisez-la avant de valider »** sous la réponse : l'IA assiste, le soignant décide.
## Étape 5 — Consigne guidée (Mode B)

- **Résident obligatoire, vérifié côté interface** : le bouton « Envoyer la consigne » reste désactivé sans résident ni texte. Le contrôle définitif reste côté n8n (le front n'est pas une barrière de sécurité).
- **Limite de 300 caractères** : `maxLength` sur le champ + compteur (orange à 30 caractères de la limite, rouge à la limite) annoncé aux lecteurs d'écran (`aria-live`).
- **Exemples cliquables qui remplacent le texte** (plutôt que de s'ajouter) : on part d'une consigne propre, modifiable ensuite. Textes dans `fr.json`.
- **Consigne uniquement en texte brut, jamais interprétée par le front** : n8n la contrôlera puis l'insérera dans l'emplacement `[INSTRUCTION SOIGNANT]` du template verrouillé (jour 3).
- **Rappel de confidentialité** sous le champ : ne pas saisir de noms ni de données personnelles, le résident étant déjà choisi.
- **Sélecteur de résident partagé** (`SelecteurResident.jsx`) entre les deux modes, pour une seule source de vérité.
## Étape 4 — Mode A (actions rapides)

- **Identifiants d'action stables** (`rapport_garde`, `resume_epa`, `points_vigilance`, `verifier_document`) : c'est ce qui sera envoyé à n8n avec la chambre ; les libellés français restent dans `fr.json` et le prompt reste côté serveur.
- **Boutons désactivés tant qu'aucune chambre n'est choisie** (+ message d'aide) : on ne peut pas lancer une action sans résident.
- **Résidents fictifs dans `src/mock/residents.json`** : liste partagée avec le Mode B (étape 5) ; noms inventés, aucune donnée réelle.
- **Pas encore d'appel à l'API** : un clic enregistre la demande `{action, chambre, resident}` et l'affiche ; la réponse simulée arrive à l'étape 7 via `api.js`.
- **Icônes SVG intégrées** : pas de bibliothèque d'icônes à ajouter ; boutons de 108 px de haut, faciles à toucher sur tablette.

## Étape 3 — Projet front

- **Vite + React (JavaScript, sans TypeScript)** : démarrage rapide, rechargement instantané, code simple à relire pour l'équipe.
- **Vite 7 avec esbuild-wasm et rollup WASM** : sur ce poste, une stratégie de contrôle d'application Windows bloque les binaires natifs (`.node`, `esbuild.exe`) installés par npm, donc Vite 8 (rolldown natif) et Vite 7 standard ne démarrent pas. Les versions WASM (`overrides` dans `package.json`) évitent tout binaire natif, au prix d'un build un peu plus lent. À retirer sur un poste sans cette restriction.
- **i18n maison (`src/i18n`)** : une fonction `t('cle.sous.cle')` lit `fr.json`. Aucun texte en dur dans les composants ; l'allemand s'ajoutera avec `de.json` de même structure, sans bibliothèque supplémentaire.
- **CSS simple, sans framework** : mise en page tablette (texte 18 px, cibles tactiles d'au moins 48 px, deux colonnes puis une seule en portrait sous 860 px).
- **`npm run dev` avec `--host`** : permet d'ouvrir l'interface depuis une vraie tablette du même réseau.

## Étape 2 — Socle docker-compose

- **Ollama hors compose** : Ollama est déjà installé sur le poste avec llama3 et nomic-embed-text ; un second conteneur dupliquerait ~5 Go de modèles. Les conteneurs l'appellent via `host.docker.internal:11434` (`extra_hosts: host-gateway` sur n8n).
- **PostgreSQL pour n8n** : base plus robuste que SQLite par défaut ; healthcheck + `depends_on: service_healthy` pour que n8n attende la base. Image 16 (n8n avertit que 17+ est préférable ; à migrer plus tard).
- **HAPI FHIR en base H2 fichier** : suffisant pour des données fictives, sans second PostgreSQL ; volume persistant `hapi_data`.
- **Ports hôte décalés** (n8n 5679, Qdrant 6335, Mosquitto 1884, HAPI 8090) : ces ports standards étaient occupés par d'autres conteneurs/outils du poste. Les ports internes restent les standards.
- **`env_file: ../.env`** plutôt que `${VAR}` : `docker compose up -d` fonctionne depuis `compose/` sans option `--env-file`.
- **Mosquitto minimal** : un listener 1883, anonyme, persistance. Acceptable en local de développement uniquement ; à sécuriser (mots de passe, TLS) avant tout déploiement.
- **Réseau `aicare` et volumes nommés** : adresses par nom de service, données conservées entre redémarrages.
- **Workflow de test** (`workflows/test-llama3.json`) : webhook → HTTP vers `/api/generate` (stream désactivé) → réponse JSON. Prompt volontairement fixe.
- **Mémoire** : sur ce poste (7,9 Go), la première tentative de Llama 3 a échoué faute de RAM libre ; relancée après libération, elle fonctionne.
