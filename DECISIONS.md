# Technische Entscheidungen – Tage 3 und 4

## Von einem lokalen Modell gesteuerter Rentenbeitrags-Agent (Werkzeuge, Wache, Vergleich) und Speicher

Details, Werkzeuge, Vergleichstabelle: `docs/cotisations.md`. Ergebnisse: `tests/resultats/sgb6-modeles.json`.

- **Das Modell wählt, der Code kontrolliert und entscheidet.** 10 Werkzeuge im Format « tools » der Chat-API von Ollama, striktes Schema; kein Werkzeug valider oder refuser; kein Parameter für Betrag, Pflegegrad oder Ergebnis einer Regel. Das Modell sieht den Fragebogen nie (kurze Ergebnisse, ohne Namen und Nummern, Alias « dossier-1 »): Eine versteckte Anweisung kann es nicht erreichen. Status und Beträge stammen aus `regles.js`; vom Modell ausgelassene Schritte werden vom Code ergänzt; ein widersprüchlicher Bericht wird gemeldet.
- **Begründung = Parameter `raison` jedes Werkzeugs** (und nicht der Text vor dem Aufruf): Kleine Modelle lassen den Text aus, der Parameter wird vom Schema validiert. Bewusste Abweichung von der Formulierung « Begründungssatz vor jedem Aufruf ». Vor dem Journal bereinigt (Namen, Adresse, Nummern entfernt).
- **In n8n auf 12 Runden ausgerollte Schleife** (kein Zyklus): Der Zustand wandert in der JSON-Sitzung von Knoten zu Knoten, ein eindeutiger Name pro Runde (keine Mehrdeutigkeit des Ausführungsindex); die Wache und die Werkzeuge liegen in einem Unter-Workflow (`97-sgb6-tour`), damit das Regelwerk nur einmal kopiert wird. Journal (`choisi_par = 'modele'`, Begründung, akzeptiert oder abgelehnt), Fortschritt und Abbruchkontrolle nach JEDER Runde. Grenzen: 2 ungültige Antworten in Folge, 12 Runden, 15 Minuten, 5 Minuten pro Antwort; Abbruch = geführte Mission mit Vermerk.
- **Aufrufe einer generativen KI: 3 benannte Knoten, nicht einer mehr** (Tests `chemins-ia` und `briques`): Verfassen (62), Extraktion SGB VI (93), SGB-VI-Steuerung pro Runde (93, 12 Knoten) und das KI-Extraktionswerkzeug des Unter-Workflows 97. Temperatur 0, num_ctx 8192 für die Steuerung, keep_alive 30 Min.; qwen3: `think: false`.
- **In der Seite einstellbares Modell**, geschlossene Liste auf Seiten von n8n (`SGB6_MODELES`): Der von der Oberfläche gesendete Name geht in eine Anfrage an Ollama, er darf nie frei sein. Die Seite zeigt den Zustand « installiert » jedes Modells (Lesen von `/api/tags`). Standardmäßig **qwen2.5:7b** (`SGB6_MODELE`): das einzige Modell, das die 3 Fälle des Vergleichs ohne Abbruch führt, mit den wenigsten Ablehnungen und am schnellsten. qwen3:8b (Favorit des Nutzers) bleibt wählbar: korrekt, aber hier (Speicher) 2-mal langsamer, ein Abbruch bei 3; llama3.1:8b bricht 3 von 3 Mal ab (Schleife von Ablehnungen).
- **Speicher**: Rechner mit 15,9 GB, Ollama nativ unter Windows (ein geladenes Modell von 5,5 bis 6,7 GB), Container mit 3,5-4,5 GB. `.wslconfig` von **11 GB auf 8 GB** umgestellt (Sicherung: `%USERPROFILE%\.wslconfig.sauvegarde-11GB`): Mit 11 GB fehlte Windows RAM, wenn ein Modell geladen war (0,3 bis 1 GB frei, Auslagerung, zeitweilige « Segmentation fault » der n8n-CLI bei Importen). Verbleibende Vorsicht: das Modell (`keep_alive: 0`) vor dem Import von Workflows entladen.
- **Ruhezustand des PCs**: Ein Zeitsprung von 3 Std. bei einem langen Versuch stammte wahrscheinlich von einem Ruhezustand; der Ruhezustand im Netzbetrieb wird bei langen Versuchen deaktiviert (`powercfg /change standby-timeout-ac 0`) und danach wieder auf 15 Minuten gesetzt (ursprünglicher Wert).
- **Grenzen**: Vergleich an 3 von 9 Fällen, ein Durchlauf pro Fall; der Test der Seite gegen n8n konnte nicht im Browser durchgeführt werden (Testsitzung von der Aktionskontrolle abgelehnt), nur im simulierten Modus.

## Rentenbeiträge an n8n angebunden (Agent als Hintergrundaufgabe, PostgreSQL, Journal, Ablage, optionales Lesen durch die KI)

Details, Webhooks, Tabellen, Tests: `docs/cotisations.md`. Gemessene Ergebnisse: `tests/resultats/sgb6-live.json`.

- **Das Regelwerk wird für n8n nicht neu geschrieben: Es wird kopiert.** Ein Code-Knoten von n8n kann keine Datei importieren; `workflows/generer.mjs` fügt `regles.js` unverändert in jeden Knoten ein, der es nutzt (die Zeile `import` wird durch die gesetzlichen Werte ersetzt, `export` entfernt) und bettet `caisse.json` ein. `tests/sgb6-n8n.test.mjs` prüft, dass jede Kopie genau die Datei enthält. Ein einziger Code, drei Verwendungen: simulierte Oberfläche, Tests, n8n.
- **Hintergrundaufgabe nach dem Vorbild des Etagenberichts**: Zeile in `soins.taches` (Typ `sgb6_agent`), Herzschlag bei jedem Schritt, Wiederaufnahme beim Neustart von n8n und Wächter der bestehenden Workflows (nichts hinzuzufügen), Ergebnis nie überschrieben, wenn die Aufgabe abgebrochen oder unterbrochen ist. **Journal und Fortschritt nach jedem der 7 Schritte geschrieben**, mit Abbruchkontrolle: Das Regelwerk ist in Schritte zerlegt (`demarrerTraitement`, `etapeControler`, `etapeCaisse`, `etapeRegles`, `etapeCalculer`, `etapeDeclaration`, `finaliserTraitement`), ein n8n-Knoten pro Schritt, der Zustand wandert als JSON; `traiterQuestionnaire` verkettet sie, und ein Test prüft, dass beide Wege dasselbe Ergebnis liefern. **Anzeigepause von 1,1 s vor jedem Schritt** (die Berechnung dauert einige ms), damit die Seite den Fortschritt des Agenten zeigt, wie die kleine Pause im simulierten Modus: eine bewusste Entscheidung der Oberfläche (≈ 7 s pro Vorgang), keine echte Langsamkeit.
- **Kein Betrag wird bei einem noch zu prüfenden Lesen durch die KI berechnet** (Fall b mit KI: 312,64 € fälschlich angezeigt, die Hälfte des richtigen Betrags, gleiche Anteile fälschlich angewendet). Beim Lesen durch die KI wird der Betrag nur berechnet, wenn alles « ok » ist (gültige Felder, keine ungewisse oder negative Regel oder Abweichung, kein verdächtiges Dokument); sonst « Betrag nicht berechnet: Daten sind zu prüfen » in der Seite, im Entwurf (Beitragsgrundlage), in den Begründungen und im Journal. Strengere Regel als « nur wenn der Wert von der Kasse abweicht »: Ein unsicheres Lesen durch ein Modell darf keine Zahl erzeugen. Ohne KI ändert sich das oben validierte Verhalten nicht (vorläufiger Betrag für f, g, i).
- **Die KI schreibt nur Felder ab.** Feste Anweisung, Temperatur 0, von Ollama erzwungenes JSON-Schema, Fragebogen von Markierungen umgeben und als Datum dargestellt. Hinzugefügte Schutzvorrichtung: Jeder von der KI gelesene Wert muss im Text des Fragebogens stehen, sonst wird er verworfen und gezählt (« erfindet nichts » vom Code geprüft, nicht nur verlangt). Fehler, unlesbare Antwort oder Überschreitung der Frist von 5 Minuten: Rückfall auf das Lesen per Regeln, gemeldet. Die versteckten Anweisungen werden vom Code auf dem gesamten Text erkannt, nicht von der KI: gleiches Ergebnis mit oder ohne Lesen durch die KI.
- **Zweiter Aufruf der generativen KI im Repository, namentlich**: `chemins-ia.test.mjs` und `briques.test.mjs` behaupteten « nur ein Knoten ruft `/api/generate` auf »; sie listen jetzt genau zwei Knoten: `62-brique-rediger.json / Sprachmodell (Ollama)` und `93-sgb6-agent.json / Extraction SGB VI (Ollama)` (Knoten umbenannt, damit der Test ihn benennt). Jeder andere Aufruf oder eine Umbenennung lässt beide Tests scheitern. Ein Test prüft, dass der Aufruf der Rentenbeiträge eine feste Anweisung, eine Temperatur von 0 und ein erzwungenes Schema hat und dass kein Weg von der KI zur Berechnung führt, ohne die Kontrolle der Antwort zu durchlaufen. `livrables.test.mjs` (Temperatur ≤ 0,2) besteht unverändert.
- **Serverseitig anhand des gespeicherten Ergebnisses beurteilte Entscheidungen**, niemals anhand der Anfrage: Validieren verlangt « Bereit zur Bestätigung » UND keine Regel und keine Abweichung außer « ok » (SQL-Abfrage auf dem gespeicherten JSON); Ablehnen verlangt eine nicht leere Begründung und eine Ausnahme; nur eine Überprüfungsaufgabe; ein entschiedener Vorgang kann weder erneut entschieden noch neu bearbeitet werden. Die Signatur ist die der Sitzung.
- **Journal ohne personenbezogene Daten**: Die Zeilen bestehen aus Zählungen und Status (« 6 ok, 0 zu prüfen, 0 nicht ausgefüllt »), niemals aus einem extrahierten Wert. Namen und Nummern leben nur in `sgb6_dossiers` (nötig, um einen Vorgang erneut zu lesen). Realer Test: Die Namen, Vornamen und Versicherungsnummern der 9 Fragebögen werden im gesamten Journal gesucht.
- **Ablage**: Base64 im JSON-Body (`.txt` oder `.pdf`, höchstens 1 MB, zweimal geprüft: dekodierte Bytes, nicht nur die angegebene Größe), PDF vom bestehenden OCR-Dienst (`compose/ocr`) gelesen und **abgelehnt, wenn OCR nötig war** (ein Scan ist kein « PDF mit Text »). Das Dokument muss mindestens die Referenz des Kassenvorgangs und den Namen der Pflegeperson enthalten. Ein verdächtiges Dokument wird akzeptiert: Der Agent meldet es. Grenze: Die Ablehnung eines Scans erfolgt nach dem OCR-Versuch, also nicht sofort.
- **Kontrollkästchen « Lesen durch die KI »** (Lesen durch die KI): im simulierten Modus standardmäßig angehakt (unverändert), **im realen Modus nicht angehakt** (es dauert mit llama3.2 mehrere Minuten).
- **Nicht erledigt**: Lesen gescannter PDFs durch die KI; Weiterentwicklung der `valeurs-legales.json` für 2027 (das fehlende Jahr ist eine ausdrückliche Ausnahme); automatischer Test der Seite selbst (von Hand im Browser geprüft, realer Modus).

## Seite « Rentenbeiträge » (Branch cotisations-retraite): Regelwerk, fiktive Daten, simulierter Modus

- **Regelwerk in reinem JavaScript** (`workflows/code/sgb6/regles.js`, ES-Modul ohne Abhängigkeit): Derselbe Code dient der Oberfläche (simulierter Modus), den Tests und später n8n. Er importiert `data/sgb6/valeurs-legales.json`; `definirValeurs()` erlaubt n8n, eigene Werte zu liefern. **Fehlendes Jahr = ausdrücklicher Fehler**, niemals ein Standardwert (2030 getestet).
- **Berechnung in ganzen Zahlen (BigInt), auf den Cent kaufmännisch gerundet bei jedem Schritt**: Grundlage = Bezugsgröße × Prozentsatz × Anteil, dann Beitrag = gerundete Grundlage × 18,6 %. Grund: In Gleitkommadarstellung kann 625,2855 € (Pflegegrad 5, Kombileistung) zu 625,28 gerundet werden; getestet wurde 625,29. Alle genauen Werte der Vorgabe geprüft (316,32; 735,63; 308,96 + 205,98; 198,62) und die 12 Kombinationen unabhängig neu berechnet.
- **Prozentsätze und Paragraphen am Gesetzestext nachgelesen** (gesetze-im-internet.de, 27.10.2026): § 166 Abs. 2 Satz 1 SGB VI (Prozenttabelle, identisch mit der Vorgabe), Satz 2 (mehrere Pflegepersonen: Aufteilung nach dem Umfang jeder Person), § 3 Satz 1 Nr. 1a (10 Std. pro Woche an mindestens 2 Tagen, Pflegegrad ≥ 2, häuslich, nicht erwerbsmäßig) und Satz 3 (mehr als 30 Std. Arbeit pro Woche = keine Versicherung). **Nicht nachgelesen**: § 5 Abs. 4 Nr. 1 SGB VI (R5, Vollrente wegen Alters) und § 19 SGB XI (R2, Definition der Pflegeperson) sind aus dem Gedächtnis zitiert; vor jedem realen Einsatz zu bestätigen.
- **Rentenversicherungsnummer**: Die Prüfziffer folgt **§ 2 Abs. 6 VKVV** (https://www.gesetze-im-internet.de/vkvv/__2.html): Buchstabe durch seine Position im Alphabet mit 2 Ziffern ersetzt (A=01 … Z=26), 12-stellige Zahl multipliziert mit 2 1 2 5 7 1 2 1 2 1 2 1, Summe der Quersummen der Produkte, Rest der Division durch 10. Der Gesetzestext gibt kein Zahlenbeispiel; der Algorithmus wurde am bekannten Beispiel 15070649C103 geprüft (Prüfziffer = 3), das aus meinem Gedächtnis und nicht aus dieser Quelle stammt. Die Kontrolle sagt nicht, dass die Nummer existiert, nur dass sie wohlgeformt ist. Eine Nummer, deren Geburtsdatum nicht dem des Fragebogens entspricht, wird gemeldet.
- **Regeln: wer liest was.** Pflegegrad (R1) und Pflegestunden (R3) stammen aus dem Vorgang der Kasse und dem Gutachten, niemals aus dem Fragebogen (Fall d: Der Fragebogen sagt 12 Std., das Gutachten 8 Std.: R3 « nein »). Die Stunden mehrerer Pflegebedürftiger werden addiert; die berücksichtigte Tageszahl ist die größte (die Tage überschneiden sich nicht zwingend, eine Annäherung auf Seiten der Pflegeperson). R4: genau 30 Std. = ok; variable Arbeitszeiten oder mehrere Beschäftigungen = ungewiss; mehr als 30 Std. = nein, auch bei variablen Zeiten. R5: Jede Angabe einer Vollrente wegen Alters oder das Fehlen einer Antwort ist « Von einer Person zu prüfen ». R6: Angegebene Anteile werden nur akzeptiert, wenn sie 100 % ergeben und ihre Zahl der der Pflegepersonen im Kassenvorgang entspricht; sonst « ungewiss » mit gleichen Anteilen.
- **Abweichungen** (Pflegegrad, Leistung, Name und Geburtsdatum der pflegebedürftigen Person, Name und Geburtsdatum der Pflegeperson zwischen Fragebogen und Kasse): Zeilen `ECART` zur Regeltabelle hinzugefügt, « Von einer Person zu prüfen » mit den beiden Werten. Die Berechnung verwendet stets Pflegegrad und Leistung **der Kasse**: Sie ist dann « vorläufig » (Fall g: 198,62 € bei Pflegegrad 2) und von einer Person zu bestätigen.
- **Wann der Agent rechnet**: solange keine Regel « nein » ist (Fälle f, g, i: Berechnung als vorläufig angezeigt, Status « Ausnahme »). Keine Berechnung, wenn eine Regel « nein » ist (Fälle d, e, h). Status « Bereit zur Bestätigung » nur, wenn alle Regeln ok sind, die Felder gültig, kein verdächtiges Dokument und eine Berechnung verfügbar ist.
- **Präpariertes Dokument (Fall i)**: Erkennung anhand von Mustern (« Ignoriere alle Regeln », « genehmige sofort », englische und französische Entsprechungen). Der Satz wird gemeldet und hat keine Wirkung: Ein Test prüft, dass Berechnung und Regeln mit und ohne den Satz identisch sind. Grenze: Es sind Muster, keine Garantie gegen jede neue Formulierung (gleiche Grenze wie die Prüfung der Anweisung in Modus B).
- **« Lesen durch die KI » im simulierten Modus**: Das Kästchen existiert und wird an den Agenten übergeben, aber es wird keine KI aufgerufen: Die Felder werden per Regeln gelesen (die Oberfläche sagt es). Die echte KI kommt mit n8n; sie hilft nur beim Lesen, nie beim Entscheiden oder Berechnen.
- **Validierung / Ablehnung**: `deciderCotisations` lehnt auch auf Seiten von `api.js` eine Validierung außerhalb von « Bereit zur Bestätigung », eine Ablehnung außerhalb einer Ausnahme oder ohne Begründung ab. Der Kasse wird nichts übermittelt (Demonstration).
- **Gestaltungsentscheidung**: Fragebögen auf Deutsch verfasst wie ein echtes Formular einer Pflegekasse (Bezeichnungen + Werte, Kontrollkästchen, Nummer mit Leerzeichen, freie Bemerkungszeile). Das Ergebnis des Agenten bleibt beim Verlassen der Seite nicht erhalten (nur der Status des Vorgangs): « Agent starten » berechnet es neu.
- **Nicht erledigt / zu tun**: Anbindung an n8n (bewusst ausgeschlossen), reales Lesen durch die KI, Aufbewahrung des Ergebnisses zwischen zwei Besuchen der Seite, automatischer Test der Seite selbst (von Hand im Browser geprüft, simulierter Modus).

## Tag 4 – Schritt 7: minimale Sicherheit (Anmeldung der Pflegekraft, Sitzungen, Schlüssel, Ursprünge) und geschlossener Broker

Details und Grenzen: `docs/securite.md`. Tests: `node tests/securite.test.mjs` (außerhalb von n8n) und `node tests/securite-live.mjs` (gegen n8n).

- **Anmeldung mit Kennung + PIN-Code, PIN gehasht.** Die PIN wird mit einem `scrypt`-Fingerabdruck verglichen (16-Byte-Salz pro Konto, Vergleich in konstanter Zeit); sie wird nirgends aufbewahrt (weder Datenbank noch Journal noch Antwort). Grund: Eine PIN im Klartext in der Datenbank wäre für jeden lesbar, der Zugriff auf die Datenbank hat; `scrypt` wird von Node geliefert (kein Modul in n8n hinzuzufügen). Eine unbekannte Kennung führt dieselbe Berechnung durch und erhält dieselbe Ablehnung wie eine falsche PIN: Nichts verrät, welche Konten existieren.
- **Sperrung: 5 Fehlversuche in 5 Minuten** bei einem bestehenden Konto → Konto während der Frist auch mit der richtigen PIN abgelehnt. Nur bestehende Konten werden gezählt, damit die Tabelle nicht mit erfundenen Kennungen wächst. Entscheidung: gleitendes Fenster in SQL berechnet, ohne Aufräumaufgabe.
- **Sitzung: zufälliges Token aus 32 Bytes, 12 Stunden, nur der SHA-256-Fingerabdruck liegt in der Datenbank.** Grund: Ein Datenbankleck liefert keine nutzbare Sitzung. Das Token bleibt im `sessionStorage` des Tabs (beim Schließen gelöscht), niemals im `localStorage`. Die Abmeldung löscht die Zeile auf Seiten von n8n.
- **Die Sitzungsprüfung ist die ERSTE Verarbeitung jedes Einstiegspunkts**, vom Generator hinzugefügt (`proteger` in `workflows/generer.mjs`) bei allen Webhooks außer der Anmeldung, dem internen Pfad und dem empfangenen Brief: Ein Test prüft, dass kein Knoten erreichbar ist, ohne « Sitzung gültig? » zu durchlaufen. Ohne Sitzung lautet die Antwort `{ "erreur": "session" }`, und die Oberfläche öffnet die Anmeldung erneut. Entscheidung für die HTTP-Antwort 200 mit einem Grund statt 401: n8n kann den Statuscode eines Webhooks im Modus « letzter Knoten » nicht festlegen, und dieser Grund genügt der Oberfläche.
- **Der Name der validierenden Pflegekraft stammt aus der Sitzung, niemals aus dem Body der Anfrage** (`valide_par` und `soignant_id`), geschrieben in `soins.validations` (neue Spalte `soignant_id`) und ins Audit-Journal. Grund: Sonst könnte jeder « im Namen » einer anderen Pflegekraft validieren. Ein Test prüft, dass ein in die Anfrage geschobenes `valide_par` ignoriert wird.
- **CORS auf die Adresse der Oberfläche beschränkt** (`http://localhost` und `http://127.0.0.1`, Ports 5173 bis 5175; Variable `AICARE_ORIGINES`, um sie zu ändern) statt `*`.
- **Geheimer Schlüssel `X-AICare-Cle` (n8n-Credential, Wert in `.env`): ein Filter, kein Geheimnis.** Die Oberfläche sendet ihn, daher ist er im Code der Oberfläche lesbar. Beibehalten, weil er Aufrufe abhält, die nicht aus der Oberfläche kommen; der eigentliche Schutz ist die Sitzung. Offen gesagt in `docs/securite.md`.
- **Interner Pfad `aicare-verifier-interne` mit eigenem Schlüssel** (`AICARE_CLE_INTERNE`, nie an die Oberfläche gesendet, im Code der Oberfläche als abwesend getestet). Grund: Der Workflow des Briefs rief « Dokument prüfen » per HTTP am öffentlichen Einstiegspunkt auf; dieser Punkt verlangt jetzt die Sitzung einer Pflegekraft, die ein automatischer Brief nicht hat. Eine direkte Ausführung des Workflows war nicht möglich: Der Einstiegspunkt antwortet sofort und setzt die KI-Analyse mehrere Minuten als Hintergrundaufgabe fort, und ein Aufruf eines Unter-Workflows hätte auf das Ende gewartet.
- **`courrier-recu` bleibt ohne Authentifizierung**: Mailpit kann keinen Header senden. Der Webhook löst nur das erneute Lesen des Mailpit-Postfachs durch n8n aus (keine Daten empfangen, nichts vom Aufrufer gelesen oder geändert). Dokumentierte Grenze; in der Produktion würde n8n das Postfach per IMAP mit eigenen Zugangsdaten lesen.
- **Fiktive Demonstrationskonten** (`martin`, `keller`, `roth`), 6-stellige PIN-Codes, zufällig in `.env` gezogen (`DEMO_PIN_*`), angelegt mit `scripts/creer-soignants.mjs`. Im simulierten Modus der Oberfläche: Konto `demo` / `123456`, keine echte Prüfung.
- **Sensoralarme nur auf ihrer Seite angezeigt** (Wunsch des Nutzers): kein Balken mehr auf den anderen Seiten, nur der rote Zähler des Tabs meldet sie. Vermerktes Risiko: Eine Pflegekraft, die auf der Seite « Dienstbericht » geblieben ist, sieht den Zähler und hört den Piepton, aber nicht die Karte.
- **Geschlossener MQTT-Broker**: `allow_anonymous false`, zwei Konten mit getrennten Rechten (`capteurs` veröffentlicht, `n8n` liest), Rechteliste `compose/mosquitto/acl`. Grund: Ein offener Broker erlaubte jedem im Netzwerk, falsche Alarme auszulösen. Passwörter zufällig von `scripts/generer-secrets.mjs` in `.env` erzeugt; die gehashte Datei wird von Git ignoriert und muss vom Benutzer des Brokers lesbar sein (`chmod 644`), sonst weigert sich der Broker zu starten.
- **TTN-Brücke ohne Umbau**: ein zweiter Auslöser im Workflow 81, der die Nachricht in das Thema `capteurs/chambre{n}/{type}` übersetzt. Das Repository enthält den deaktivierten Knoten ohne Konto; der Importeur aktiviert ihn mit den Werten aus `.env`. Der TTN-Schlüssel steht nie in einem Workflow oder im Repository (getestet). Nur Lesen des Datenverkehrs, verschlüsseltes MQTT (8883), da der Port 1883 des TTN-Servers nicht verschlüsselt ist. Aus einer TTN-Nachricht werden nur das Zimmer und der Alarmtyp (geschlossene Liste) übernommen.
- **Die Workflows werden am Ende der Generierung geschrieben** (`generer.mjs`), weil der Schutz der Einstiegspunkte alle Hilfsfunktionen braucht; die Zeilenenden des Codes der Knoten werden normalisiert.
- **Offener Punkt**: kein HTTPS, keine Rollen und keine Kontenverwaltung in der Oberfläche, Token 12 Stunden gültig, auch wenn der Tab ohne Abmeldung geschlossen wird (siehe `docs/securite.md`).
## Tag 4 – Schritt 6: Dokumente automatisch und Umbau der Oberfläche auf drei Seiten

- **Drei Geschäftsprozesse, drei Seiten** (Wunsch des Nutzers): « Dienstbericht » (erster Prozess: eine einmal gewählte Person, zwei Modi zur Wahl, Schnellaktionen und geführte Anweisung, dazu der Bericht einer ganzen Etage), « Alarme » (Sensoren, mit Dringlichkeitsbalken und Signalton) und « Dokumente » (Briefe und Neuigkeiten der ePA, ohne Lärm). Eine Dokumentenwarnung erscheint nie auf der Seite der Sensoralarme. Der Dringlichkeitsbalken bleibt auf den anderen Seiten sichtbar, nur für Sensoralarme.
- **Eingegangener Brief**: Mailpit benachrichtigt n8n per Webhook (**es hat kein IMAP**, nur SMTP und POP3; mit einem echten KIM-Postfach wird der Webhook durch einen « Email Trigger (IMAP) » ersetzt). n8n liest nur die **Kennung** der Benachrichtigung, liest die Nachricht über die API von Mailpit erneut, extrahiert den Text (OCR bei einem Scan), identifiziert die Person durch den **Code** (Name UND Geburtsdatum, nie erraten: Diese Kennung hängt nicht vom Modell ab), indexiert in `a_verifier`, wendet die Sicherheitsregeln an und legt eine Warnung (rot, Achtung oder Information) auf der Seite Documents an.

- **Validierung → RAG**: Nur die Validierung eines Berichts « Dokument prüfen » kann den Brief in die Intelligenzquellen bringen (Collection `patients`, Typ `lettre_validee`), und **nur wenn die Regeln darin keinen Widerspruch gefunden haben**; bei einem Widerspruch wird die Validierung gespeichert, aber der Brief bleibt in `a_verifier` bis zur Klärung durch die Ärztin bzw. den Arzt (zu diskutierende Entscheidung: Ein widersprüchlicher Brief wird nicht in die verlässlichen Fakten aufgenommen).
- **Neuigkeiten der ePA**: eine Informationswarnung, wenn die bereits importierte ePA einer Person neuen oder geänderten Inhalt erhält (der erste Import meldet nichts). An der echten Abfrage in einer abgebrochenen Transaktion geprüft; die zur Speicherersparnis angehaltenen ePA-Mocks wurden nicht neu gestartet.
- **« Extraire_faits » identifiziert die Person nicht** (anders als in der Aufgabenstellung formuliert): Die Identifizierung über Name und Geburtsdatum erfolgt durch den Code, da ein Identitätsfehler schwerer wiegt als ein nicht zugeordneter Brief.
- **Oberfläche**: neues Logo (Symbol des Logos des Nutzers in der Kopfzeile, Favicon), verlorene Verbindung gemeldet, Texttests (`tests/i18n.test.mjs`).
- **Während des Schritts korrigierte Fehler der Oberfläche**: ein Kompilierfehler (falsch geschriebene Zeichenkette in der Verlaufsseite) und als rohe Schlüssel angezeigte Texte (doppelter Schlüssel `alertes` in `de.json`) wurden mir vom Nutzer gemeldet; die Oberfläche wird jetzt **vor der Auslieferung im Browser geprüft**, im simulierten und im realen Modus.
- **Praxisversuch** (`node tests/courrier-live.mjs`, 16 Prüfungen): Briefe Weber (31 s), Fischer, unbekannt, Scan Wagner (110 s, OCR), erneutes Senden ohne Duplikat, Nachricht ohne Anhang ohne Wirkung, Validierungen (Fischer hinzugefügt, Weber abgelehnt), ePA.

## Tag 4 – Schritt 4: verlässliche Hintergrundaufgaben (Herzschlag, Abbruch, Wiederaufnahme)

In der Praxis geprüft (n8n mit einer Aufgabe `en_cours` neu gestartet: in wenigen Sekunden unterbrochen, Ereignis `tache_interrompue` Ursache `redemarrage` im Audit-Journal).

## Tag 4 – Schritt 1: Anti-Erfindungs-Filter (« 0 Sätze ohne Quelle »)

- **Feststellung** (Versuch der Etage 2, Llama 3.2): Ein kleines Modell schreibt Sätze, die die Quellen nicht enthalten (« erhebliche Diurese », « Dosis der Antihistaminika anpassen »). Die Warnungen meldeten sie, ohne sie zu verhindern. Ein Prompt kann das nicht garantieren: Der Code muss es durchsetzen.
- **Das Modell schreibt keinen freien Text mehr.** Für die fünf Textprompts (`generer_sbar`, `resume_epa`, `points_vigilance`, `contexte_alarme`, `consigne_guidee`, `sortie: phrases`) liefert es ein JSON `{"phrases": [{"section", "phrase", "source_id"}]}`. Dieses Format wird **von Ollama bei der Generierung erzwungen** (strukturierte Ausgabe mit JSON-Schema, einschließlich der Aufzählung der Rubriken) und nicht nur im Prompt verlangt; geprüft mit Ollama 0.40.9 und Llama 3.2.
- **Jeder Fakt trägt eine Kennung** (F1, F2 …) im Block QUELLENFAKTEN; der Satz bezeichnet den Fakt, aus dem er stammt. Ein Satz = nur ein Fakt (keine Verschmelzung von Fakten verschiedener Quellen mehr).
- **Eine codierte Kontrolle, ohne KI**, im Knoten « Antwort prüfen », entfernt jeden Satz, bei dem: die Kennung kein gelieferter Fakt ist; eine Zahl, Dosis, Uhrzeit oder ein Datum nicht in DIESEM Fakt steht; ein Medikament (Liste von Endungen + Namen, denen in den Fakten eine Dosis folgt) nicht in DIESEM Fakt steht; ein Urteil (« erhöht », « wichtig », « stabil » …) nicht von DIESEM Fakt formuliert wird; mindestens 40 % der Inhaltswörter (mindestens 2) darin fehlen; eine andere Person erwähnt wird; oder der Satz doppelt oder außerhalb der Rubrik ist.
- **Der Text wird vom Code zusammengesetzt**: Rubriküberschriften, behaltene Sätze und die Quelle in eckigen Klammern **nach dem zitierten Fakt** hinzugefügt (das Modell kann keine Quelle mehr falsch zitieren). Eine Rubrik ohne Satz zeigt « Information nicht verfügbar. », vom Code geschrieben.
- **Die entfernten Sätze werden gesondert aufbewahrt** (`retirees`, Spalte `soins.brouillons.retirees`, Anzahl im Audit-Journal) und in einem einklappbaren Abschnitt « Entfernt, da nicht belegt » angezeigt: Die Pflegekraft sieht alles, was verworfen wurde; nichts davon gelangt in den Text, in die Validierung, ins RAG oder in die Übermittlung.
- **Ein ungültiges JSON ergibt keinen Text**; ein durch die Längengrenze abgeschnittenes JSON wird Satz für Satz gerettet (der letzte, unvollständige wird ignoriert).
- **Bewusst in Kauf genommener Kompromiss**: Die Kontrolle ist streng, sie kann einen korrekten, schlecht formulierten Satz entfernen. Besser ein kürzerer Bericht als ein erfundener Satz im Nachtdienst. Die alten Kontrollen (Zuordnung, Begriffe, Wiederholungen …) laufen anschließend auf dem zusammengesetzten Text und bleiben Warnungen.
- **Verneinungen**: Eine Verneinung des Fakts kann weder verloren gehen noch hinzugefügt werden (« kein Bewusstseinsverlust » wird nie zu « Bewusstseinsverlust »: Die beiden Sätze teilen alle Wörter, nur diese Kontrolle unterscheidet sie). « kein » und « ohne » sind gleichwertig.
- **Grenze**: Der Filter prüft, dass der Satz von seinem Fakt gestützt wird, nicht dass die Formulierung den gesamten Sinn bewahrt (subtilere Umkehrungen, Reihenfolge der Ereignisse, Kausalität). Das Gegenlesen durch die Pflegekraft bleibt Pflicht.
- **Prompts auf 1.1.0 angehoben** (`consigne_guidee` 1.2.0) und Regeln auf 1.3.0; die Datei `prompts/tests/points_vigilance.json` wurde korrigiert (die Referenzantwort verschmolz zwei Fakten).
- **Tests**: `node tests/anti-invention.test.mjs` (19 Tests: Uhrzeiten, Werte, Dosen, Urteile, Medikamente, falscher Fakt, Injektion, Duplikat, ungültiges oder abgeschnittenes JSON, Mutation jeder Zahl jedes Fakts) und `tests/prompts.test.mjs` (in JSON umgewandelte Referenzantworten).

## Tag 3 – Schritt 4: Dienstbericht (pro Person und pro Etage), Aufnahme ins RAG und Übermittlung

- **Der SBAR-Dienstbericht (letzte 12 Stunden) existiert in zwei Maßstäben**: eine Person (bestehende Schaltfläche, `aicare-action`) und eine ganze Etage (`aicare-etage`). Für eine Etage ist der Prompt in n8n **auf `generer_sbar` festgelegt**, und die Oberfläche sendet nur eine Etagennummer (eine geprüfte ganze Zahl): kein freier Text.
- **Etage = asynchrone Aufgabe.** Ein Bericht braucht 2 bis 6 Minuten; eine Etage mit 4 Personen 10 bis 25, weit mehr als eine vernünftige HTTP-Anfrage. `aicare-etage` legt eine Zeile in `soins.taches` an, **antwortet sofort** (Knoten « Sofort antworten » mitten im Workflow) und macht weiter; die Oberfläche fragt `aicare-tache` alle 4 Sekunden ab und zeigt jeden Bericht an, sobald er bereit ist. Die Personen werden **nacheinander** bearbeitet (`Execute Workflow` im Modus « jedes Element »): Der Rechner mit 8 GB lässt nicht zwei Generierungen gleichzeitig laufen. Ein Fehler bei einer Person wird in der Aufgabe vermerkt (`termine_avec_erreurs`) und hält die anderen nicht an.
- **Ein einziger Schreibbaustein für alle Wege**: Der Unter-Workflow `67-brique-rapport-garde` verkettet dieselben Bausteine wie Modus A (Suchen, gesperrte Vorlage, Verfassen). Kein neuer Aufruf der KI; ein Test prüft, dass keiner der neuen Workflows `/api/generate` enthält.
- **Die Aufgabe behält nur Entwürfe.** Nichts wird als validiert gespeichert, solange die Pflegekraft nicht auf « Etage bestätigen » geklickt hat. Jeder Bericht bleibt vor der Validierung bearbeitbar.
- **Nach der Validierung zwei Wirkungen, in einem gemeinsamen Baustein (`66-brique-apres-validation`)**: (1) Der validierte Text wird **dem RAG hinzugefügt** (Collection `patients`, Quelle « Bestätigter Bericht », Typ `rapport_valide`, der Person zugeordnet) durch den bestehenden Indexeur (Duplikatsperre per SHA-256-Fingerabdruck); (2) er wird **an das nächste Team übermittelt** durch eine in Mailpit gesendete Nachricht (das simulierte Postfach, wie KIM) und in `soins.transmissions` vermerkt. Das Audit-Journal erhält die Ereignisse `ajout_rag` und `transmission`.
- **Der dem RAG hinzugefügte und übermittelte Text wird in der Tabelle der Validierungen erneut gelesen**, über die numerische Kennung der Validierung, niemals aus der empfangenen Anfrage: Es wird nur übermittelt, was nach Kontrolle des Entwurfs gespeichert wurde. Nur eine Validierung mit der Aktion `generer_sbar` löst diese beiden Wirkungen aus; eine validierte ePA-Zusammenfassung, Aufmerksamkeitspunkte oder eine Antwort auf eine Anweisung werden gespeichert, aber weder übermittelt noch dem RAG hinzugefügt.
- **Validierung eines Stapels** (`aicare-valider-lot`): Jeder Bericht durchläuft einzeln den Baustein « Speichern » (Entwurf erforderlich, nur eine Validierung pro Entwurf), dann fasst **eine einzige Nachricht** die Etage zusammen. Ein abgelehnter Bericht (bereits validiert, nicht gefunden) hält die anderen nicht auf; er wird in der Antwort aufgelistet.
- **Ein Übermittlungsfehler macht die Validierung nicht rückgängig.** Der Status `echec` wird vermerkt, die Oberfläche sagt es deutlich (« das nächste Team wurde nicht benachrichtigt»), statt es als Erfolg anzuzeigen.
- **Ein validierter Bericht wird von einem neuen Bericht nie als Fakt erneut gelesen.** Sonst würden etwaige Fehler eines früheren SBAR (oder seine Auslassungen) in den nächsten übernommen. « Suchen » ignoriert den Typ `rapport_valide`, außer der Prompt verlangt es (`rapports_valides: true` im Kopf der Datei; nur `consigne_guidee`, auf 1.1.0 angehoben, tut dies). Eine Pflegekraft kann also in Modus B den Verlauf abfragen, mit der gut sichtbaren Quelle « Bestätigter Bericht ».
- **Der KIM-Konnektor wird nicht gestört**: Er liest nur Mailpit-Nachrichten mit Anhang; die Übermittlungsnachricht hat keinen (Test).
- **Fiktiver Empfänger** `equipe-suivante@sonnenhof.example.test`: kein echtes Postfach, kein echtes KIM. Die Nachrichten sind in Mailpit einsehbar (`http://localhost:8025`).
- **Grenzen**: keine Identität der Pflegekraft (`valide_par` bleibt « Pflegekraft (nicht identifiziert) », solange es keine Authentifizierung gibt); nur ein nächstes Team; die laufende Aufgabe kann nicht über die Oberfläche abgebrochen werden; wenn n8n während einer Etage neu startet, bleibt die Aufgabe `en_cours` (neu zu starten).
- **Werkzeuge**: `node workflows/importer.mjs --seulement=66,74` importiert nur bestimmte Workflows erneut (das Ganze dauert mehrere Minuten); `node tests/etage-live.mjs 2` wiederholt den Praxisversuch durchgängig.

## Tag 2 – Schritt 5: Planung, Duplikatsperre und Journal

- **Planung: 4-mal täglich und nicht alle 5 Minuten** (Vorgabe aktualisiert: « alle 5 Min. » durch « 4-mal täglich » ersetzt). Alle 6 Stunden: 00:00, 06:00, 12:00 und 18:00 (Berliner Zeit, `timezone` in jedem Workflow festgelegt). Die 4 Konnektoren sind **um 10 Minuten versetzt** (Pflege :00, FHIR :10, Dateien :20, ePA :30), um Ollama und den Speicher des Rechners nicht gleichzeitig zu belasten. Zu beachtende Folge: Eine Information der Pflegesoftware kann bis zu 6 Stunden warten, bis sie im RAG ist; die Webhooks `import-*` erlauben einen sofortigen Import, und die Frequenz ändert sich durch Änderung von `HEURES` in `workflows/generer.mjs`.
- **Duplikatsperre per SHA-256-Fingerabdruck, VOR dem Embedding geprüft**: Der Indexeur liest das Journal (eine einzige Abfrage für alle Abschnitte), behält nur die unbekannten Fingerabdrücke und vektorisiert oder sendet nichts an Qdrant, was sich nicht geändert hat. Gemessen: Durchlauf 1 = 93 Abschnitte importiert; Durchläufe 2 und 3 = 0 importiert, 93 ignoriert. Das spart vor allem die Zeit des Embeddings, auf diesem Rechner sehr langsam.
- **Doppelter Schutz**: Die Kennung des Qdrant-Punktes ist stabil (Quelle, Referenz, Nummer des Abschnitts). Selbst wenn das Journal geleert würde, würde ein erneuter Import dieselben Punkte überschreiben, statt sie zu duplizieren.
- **Ein geänderter Abschnitt wird erneut importiert**: Sein Fingerabdruck ändert sich, er passiert die Duplikatsperre und ersetzt den bestehenden Punkt. Das Journal behält die alten Versionen (Audit-Verlauf), mit Bedingung `UNIQUE(source, empreinte)`.
- **Import-Journal (`soins.journal_imports`)**: eine Zeile pro Abschnitt (Quelle, Referenz#Abschnitt, patient_id, Fingerabdruck, Collection/Typ, Datum), **erst nach** erfolgreichem Schreiben in Qdrant geschrieben: Ein Fehler unterwegs wird nie als importiert markiert und beim nächsten Durchlauf erneut versucht.
- **Zweig « nichts Neues »**: Sind alle Abschnitte bekannt, liefert der Workflow `{morceaux_indexes: 0, ignores_deja_importes: n}`, ohne Ollama oder Qdrant aufzurufen.
- **Automatisierter Test `tests/test-du-soir.mjs`**: 3 Durchläufe der 4 Konnektoren; prüft stabile Punktzahl, kein doppeltes Tripel Quelle/Referenz/Abschnitt in den 3 Collections, stabiles Journal ohne doppelten Fingerabdruck und dass « Herr Weber Sturz » mindestens 3 Quellen liefert.
## Tag 2 – Schritt 4: n8n-Konnektor-Workflows

- **Architektur: 4 Konnektoren + 1 gemeinsamer Unter-Workflow « Indexierer »** (`workflows/00-indexeur.json`). Jeder Konnektor tut nur « seine Quelle lesen und Dokumente erzeugen »; Aufteilung, Embedding und Schreiben in Qdrant sind einmal geschrieben. Eine Quelle hinzuzufügen (z. B. KIM) = ein Konnektor mehr, ohne den Indexeur anzutasten.
- **Die Workflows werden erzeugt** (`node workflows/generer.mjs`) aus Dateien `workflows/code/*.js`: Der Code jedes Knotens ist eine echte lesbare Datei, durchsehbar und außerhalb von n8n testbar (`tests/indexeur-decoupage.test.mjs`), statt in JSON unterzugehen. Die erzeugten JSON-Dateien sind versioniert (sie werden importiert); `node workflows/importer.mjs` importiert sie, veröffentlicht die Trigger und startet n8n neu.
- **Kein Secret in den Workflows**: Das PostgreSQL-Passwort ist ein n8n-Credential, das `importer.mjs` aus der `.env` anlegt; die JSON-Dateien enthalten nur seine Kennung. Die Adressen (Qdrant, Ollama …) sind fest in die Knoten geschrieben, da n8n 2 den Zugriff auf Umgebungsvariablen in den Knoten blockiert.
- **n8n 2: Ein Unter-Workflow muss veröffentlicht sein**, sonst schlägt der Aufruf fehl (« Workflow is not active »). `importer.mjs` veröffentlicht daher auch den Indexeur.
- **Aufteilung 300–500 Wörter** (Ziel 400, nie mehr als 500, ein kurzer letzter Abschnitt wird an den vorigen angehängt): Ein Dokument mit weniger als 500 Wörtern bleibt ganz. Eine Pflegenotiz (30 bis 60 Wörter) bleibt also **ein einziger Abschnitt mit ihrem genauen Datum**: Die Notizen eines Tages zu Blöcken von 300 Wörtern zu verschmelzen, würde den Filter « letzte 12 Stunden » zerstören. Die Aufteilung greift bei langen Dokumenten (Protokolle, Briefe, OCR-Texte).
- **Stabile Kennung des Qdrant-Punktes** = Hash aus (Quelle, Referenz, Nummer des Abschnitts): Dasselbe Dokument erneut zu importieren überschreibt denselben Punkt, nie ein Duplikat, auch ohne Journal. **SHA-256-Fingerabdruck des Inhalts** (Text + Datum + Person + Typ) im Payload: Er dient der Duplikatsperre und dem Journal von Schritt 5 (nicht erneut embedden, was sich nicht geändert hat).
- **Der Name der Person wird dem vektorisierten Text hinzugefügt** (« Herr Hans Weber (Zimmer 12) – … ») und das Präfix `search_document:` von nomic-embed-text verwendet: Ohne das findet die Suche « Herr Weber Sturz » die Abschnitte einer bestimmten Person nicht.
- **Eine einzige `patient_id`**: Die Konnektoren FHIR und ePA finden die Person über die Zuordnungstabelle (FHIR-Kennung, KVNR), niemals über den Namen.
- **Dateien: OCR durch einen kleinen Dienst** (`compose/ocr`, OCRmyPDF + Tesseract deu/fra/eng, per HTTP aufgerufen). Ein PDF mit Text wird mit pdftotext gelesen (schnell, getreu); nur Scans durchlaufen die OCR. Gewählt, weil der Knoten « Befehl ausführen » von n8n 2 deaktiviert ist und n8n keinen Zugriff auf Docker hat. Der Ordner `data/fichiers/` ist schreibgeschützt in `~/.n8n-files` eingebunden (der einzige von n8n 2 lesbare Ordner).
- **Zuordnung gescannter Dokumente**: Ein Dokument wird einer Person nur zugeordnet, wenn **Name UND Geburtsdatum** des Textes genau einer Person entsprechen (Namensvettern unterscheiden sich nur durch das Datum). Sonst kommt es nach `a_verifier` (`identite_inconnue` oder `identite_ambigue`): Eine Identität wird nie erraten.
- **FHIR: Antwort als JSON erzwungen** (`Accept: application/fhir+json` + Antwortformat JSON): HAPI liefert sonst HTML, und der Typ `application/fhir+json` wird von n8n nicht als JSON erkannt. `_lastUpdated` dient als Datum der Dokumente: Es ändert sich nur, wenn sich die Ressource ändert. Die vollständige Liste eines Typs wird immer erneut gelesen, um das gesamte Dokument einer Person zu rekonstruieren (nie ein Teilabschnitt, der den Rest überschreiben würde).
- **ePA als FHIR-JSON gelesen** (Direktzugriff, ohne VAU) und nach KVNR gefiltert; die dem Haus unbekannten Patienten aus den Beispielen von gematik werden ignoriert.
- **Postgres: `executeOnce`** bei den Knoten, die einem Knoten mit mehreren Zeilen folgen: n8n führt einen Knoten einmal pro empfangenem Element aus, was 351 Abschnitte statt 47 ergeben hatte (Fehler gefunden und behoben).
- **Außerhalb des Umfangs dieses Schritts**: Planung alle 5 Minuten, Duplikatsperre per Fingerabdruck vor dem Embedding und Import-Journal (Schritt 5). Das **KIM-Postfach (Arztbriefe in Mailpit) hat noch keinen Konnektor**: Es stand nicht in der Liste der 4 verlangten Workflows; es wird `a_verifier` speisen.
- **Gemessenes Ergebnis** (eine Ausführung jedes Konnektors): 47 Abschnitte (Pflegesoftware) + 24 (FHIR) + 16 (ePA) + 1 Scan (Dateien) = 88 in `patients`; 5 Protokolle in `connaissances`. Die Suche « Herr Weber Sturz » liefert Abschnitte der Pflegesoftware, der ePA und der Krankenhausdatenbank.
## Tag 2 – Schritt 3: Qdrant-Collections und Zuordnung der Kennungen

- **3 Collections, 768 Dimensionen, Distanz Cosine** (`patients`, `connaissances`, `a_verifier`): 768 = Dimension von `nomic-embed-text`, an einem echten Embedding geprüft (Testpunkt eingefügt, mit einem Score von 1,0 wiedergefunden, dann gelöscht). Cosine passt zu Text-Embeddings (nur der Winkel zählt, nicht die Länge).
- **Aufgabe jeder Collection**: `patients` = einer Person zugeordnete Abschnitte (eine einzige nach `patient_id` gefilterte Collection statt einer pro Person: einfacher abzufragen und zu planen); `connaissances` = Protokolle, ohne Patient; `a_verifier` = zu prüfende eingehende Dokumente (Briefe, mehrdeutige Identität, Widerspruch), getrennt, damit eine ungeprüfte Information nie als verlässlich dargestellt wird.
- **Payload-Indizes** auf den gefilterten Feldern: `patient_id`, `chambre`, `source`, `type`, `empreinte` (keyword), `date` (datetime, für « die letzten 12 Stunden »), dazu `theme` (connaissances) und `statut`/`motif` (a_verifier). Ohne Index sind die Qdrant-Filter langsam, sobald die Collection wächst.
- **Anlegen ohne Löschen**: Das Skript legt eine Collection nie neu an; findet es eine mit anderer Dimension oder Distanz, bricht es ab, statt Daten zu löschen.
- **Eine einzige `patient_id` (`PAT-00x`) für alle Systeme** über `soins.correspondance` (Pflegesoftware, FHIR, KVNR der ePA, Sensor, Zimmer) und die flache Sicht `soins.v_correspondance`.
- **SQL-Funktionen zur Auflösung**: `soins.resoudre_patient(systeme, identifiant)` und `soins.trouver_par_identite(nom, naissance)`. Bei Namensvettern liefert sie 0 Zeilen, wenn unbekannt, und rät nie: Der Aufrufer legt das Dokument dann in `a_verifier` ab. Eindeutiger Index `(nom, prenom, date_naissance)`.

# Technische Entscheidungen – Tag 1

## Schritt 7 — Warnungen, fiktive Antworten und Schicht api.js

- **`api.js` ist der einzige Zugangspunkt zu den Daten**: Die Oberfläche ruft nur `demander()` und `enregistrer()` auf. An Tag 3 zu n8n zu wechseln heißt, `VITE_MOCK=false` zu setzen, ohne die Oberfläche neu zu schreiben.
- **Schalter `VITE_MOCK` (Standard `true`)**, gelesen aus der `.env` im Stammverzeichnis (`envDir: '..'` in `vite.config.js`). Nur mit `VITE_` beginnende Variablen sind für den Browser sichtbar: Die Passwörter der `.env` werden dem Front nie offengelegt.
- **Vertrag mit n8n**: Modus A `POST /aicare-action {action, chambre}`; Modus B `POST /aicare-consigne {chambre, consigne}`; Validierung `POST /aicare-valider {…, texte, sources, modifiee}`. Antwort: `{texte, sources[], alertes[{type, message}]}`. Die Namen der Webhooks können sich an Tag 3 ändern.
- **`mock.json`**: eine simulierte Antwort pro Aktion + eine für Modus B, mit Variablen `{resident}`, `{chambre}`, `{consigne}`; fiktive Daten (z. B. Herr Weber, Zimmer 12). Die zitierten Quellen entsprechen den Intelligenzquellen: Pflegesoftware, ePA, Arztbrief, Krankenhausdatenbank (FHIR), Sensoren, Telematikinfrastruktur (Gesundheitswesen in Deutschland).
- **Roter Balken unter der Kopfzeile, volle Breite** (und nicht in der Antwortspalte): Auf einem Tablet im Hochformat liegt die Antwort weiter unten, die Warnung muss ohne Scrollen sichtbar bleiben. `role="alert"` für Screenreader. Zwei Typen: Sensoralarm und Widerspruch zwischen Dokumenten.
- **Warnszenarien des Mocks**: Dienstbericht und Aufmerksamkeitspunkte → Bettsensor-Alarm (LoRaWAN); Dokument prüfen → Widerspruch (Amoxicillin verordnet / Penicillinallergie). ePA-Zusammenfassung und Modus B → keine Warnung.
- **Lade- und Fehlerzustände**: Meldung während der Generierung (Schaltflächen deaktiviert, um doppelte Anfragen zu vermeiden); bei einem Speicherfehler bleibt der Text der Pflegekraft erhalten.
## Schritt 6 — Antwort und Validierung

- **Form einer Antwort: `{ texte, sources[] }`**: Der Text enthält die Zitate bereits in eckigen Klammern; die Liste der Quellen wird als Etiketten `[Pflegesoftware]`, `[ePA]` … wiederholt, um sie auf einen Blick zu sehen. Diese Form wird die des n8n-Webhooks sein.
- **Bearbeitbares Textfeld mit Anzeige « • geändert »**: Die Pflegekraft behält die Kontrolle; man weiß, ob der validierte Text vom Text der KI abweicht (`modifiee` wird an `onValider` übergeben, nützlich für die Nachvollziehbarkeit).
- **Jede Änderung hebt die vorige Validierung auf**: Man kann nicht glauben, eine nachträglich bearbeitete Version sei gespeichert.
- **Validierung = angezeigte Bestätigung mit Uhrzeit**; die echte Speicherung (n8n / Datenbank) wird in Schritt 7 und an Tag 3 über `api.js` angebunden. Grüne Schaltfläche (Farbe der Validierung), deaktiviert, wenn der Text leer ist.
- **Hinweis « Lesen Sie sie durch und korrigieren Sie sie bei Bedarf vor der Bestätigung »** unter der Antwort: Die KI unterstützt, die Pflegekraft entscheidet.
## Schritt 5 — Geführte Anweisung (Modus B)

- **Bewohner Pflicht, auf Seiten der Oberfläche geprüft**: Die Schaltfläche « Anweisung senden » bleibt ohne Bewohner und Text deaktiviert. Die endgültige Kontrolle bleibt auf Seiten von n8n (das Front ist keine Sicherheitsschranke).
- **Grenze von 300 Zeichen**: `maxLength` am Feld + Zähler (orange 30 Zeichen vor der Grenze, rot an der Grenze), Screenreadern über `aria-live` angesagt.
- **Anklickbare Beispiele, die den Text ersetzen** (statt sich anzuhängen): Man beginnt mit einer sauberen Anweisung, anschließend änderbar. Texte in `de.json`.
- **Anweisung nur als einfacher Text, vom Front nie interpretiert**: n8n wird sie prüfen und dann in den Platz `[ANWEISUNG PFLEGEKRAFT]` des gesperrten Templates einfügen (Tag 3).
- **Datenschutzhinweis** unter dem Feld: keine Namen und keine personenbezogenen Daten eingeben, da die Person bereits gewählt ist.
- **Gemeinsame Bewohnerauswahl** (`SelecteurResident.jsx`) für beide Modi, für eine einzige Wahrheitsquelle.
## Schritt 4 — Modus A (Schnellaktionen)

- **Stabile Aktionskennungen** (`rapport_garde`, `resume_epa`, `points_vigilance`, `verifier_document`): Das wird mit dem Zimmer an n8n gesendet; die Bezeichnungen stehen in `de.json`, und der Prompt bleibt serverseitig.
- **Schaltflächen deaktiviert, solange kein Zimmer gewählt ist** (+ Hilfsmeldung): Man kann keine Aktion ohne Bewohner starten.
- **Fiktive Bewohner in `src/mock/residents.json`**: mit Modus B geteilte Liste (Schritt 5); erfundene Namen, keine echten Daten.
- **Noch kein API-Aufruf**: Ein Klick speichert die Anfrage `{action, chambre, resident}` und zeigt sie an; die simulierte Antwort kommt in Schritt 7 über `api.js`.
- **Integrierte SVG-Symbole**: keine Symbolbibliothek hinzuzufügen; Schaltflächen von 108 px Höhe, auf einem Tablet leicht zu berühren.

## Schritt 3 — Front-Projekt

- **Vite + React (JavaScript, ohne TypeScript)**: schneller Start, sofortiges Neuladen, einfacher Code, leicht für das Team zu lesen.
- **Vite 7 mit esbuild-wasm und rollup-WASM**: Auf diesem Rechner blockiert eine Windows-Anwendungssteuerungsrichtlinie die von npm installierten nativen Binärdateien (`.node`, `esbuild.exe`), daher starten Vite 8 (natives rolldown) und Standard-Vite 7 nicht. Die WASM-Versionen (`overrides` in `package.json`) vermeiden jeden nativen Binärcode, auf Kosten eines etwas langsameren Builds. Auf einem Rechner ohne diese Einschränkung zu entfernen.
- **Eigene i18n (`src/i18n`)**: Eine Funktion `t('cle.sous.cle')` liest `de.json`. Kein fest eingetragener Text in den Komponenten; weitere Sprachen kommen als zusätzliche JSON-Dateien gleicher Struktur hinzu, ohne zusätzliche Bibliothek.
- **Einfaches CSS, ohne Framework**: Tablet-Layout (Text 18 px, Touch-Ziele von mindestens 48 px, zwei Spalten, dann eine einzige im Hochformat unter 860 px).
- **`npm run dev` mit `--host`**: erlaubt es, die Oberfläche von einem echten Tablet im selben Netzwerk zu öffnen.

## Schritt 2 — docker-compose-Basis

- **Ollama außerhalb des Compose**: Ollama ist bereits auf dem Rechner mit llama3 und nomic-embed-text installiert; ein zweiter Container würde ~5 GB Modelle duplizieren. Die Container rufen es über `host.docker.internal:11434` auf (`extra_hosts: host-gateway` bei n8n).
- **PostgreSQL für n8n**: robustere Datenbank als das Standard-SQLite; Healthcheck + `depends_on: service_healthy`, damit n8n auf die Datenbank wartet. Image 16 (n8n weist darauf hin, dass 17+ vorzuziehen ist; später zu migrieren).
- **HAPI FHIR mit H2-Dateidatenbank**: genügt für fiktive Daten, ohne zweites PostgreSQL; persistentes Volume `hapi_data`.
- **Versetzte Host-Ports** (n8n 5679, Qdrant 6335, Mosquitto 1884, HAPI 8090): Diese Standardports waren von anderen Containern/Werkzeugen des Rechners belegt. Die internen Ports bleiben die Standardports.
- **`env_file: ../.env`** statt `${VAR}`: `docker compose up -d` funktioniert aus `compose/` ohne die Option `--env-file`.
- **Minimales Mosquitto**: ein Listener 1883, anonym, Persistenz. Nur in der lokalen Entwicklung akzeptabel; vor jedem Einsatz zu sichern (Passwörter, TLS).
- **Netz `aicare` und benannte Volumes**: Adressen über Dienstnamen, Daten bleiben zwischen Neustarts erhalten.
- **Testworkflow** (`workflows/test-llama3.json`): Webhook → HTTP an `/api/generate` (Stream deaktiviert) → JSON-Antwort. Bewusst fester Prompt.
- **Speicher**: Auf diesem Rechner (7,9 GB) scheiterte der erste Versuch mit Llama 3 an fehlendem freiem RAM; nach Freigabe neu gestartet, funktioniert er.

## Schritt 1 — Vorbereitung
